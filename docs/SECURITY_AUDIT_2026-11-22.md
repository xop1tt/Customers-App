## Находки

### H1. Подмена учётной записи через ссылку из браузера (исправлено)

`cloud/auth.rs` `handle_callback` принимал любую ссылку `leadgenerator://auth/callback#access_token=…&refresh_token=…`
и сразу сохранял сессию, а `app/session.rs:497` `handle_auth_url` открывал облако этой учётной записи; при
`type=recovery` — ещё и окно «Новый пароль». Схему ссылок может открыть любая веб-страница (браузер лишь
спрашивает «Открыть Customers?»), поэтому злоумышленник подставлял токены своей учётной записи:

* пользователь незаметно оказывается в чужом аккаунте и вносит туда своих клиентов и сделки (злоумышленник их
  видит), или задаёт «новый пароль» чужому аккаунту, думая, что восстанавливает свой;
* текущая сессия перезаписывалась до любой проверки.

Исправление (только приложение): ядро запоминает адреса, на которые оно само запросило письмо (регистрация,
повторное письмо, восстановление, смена адреса — оба адреса), на 24 часа. Ссылка принимается, только если её
учётная запись совпадает с ожидаемым адресом, и один раз; сессия сохраняется только после проверки, текущий вход
не трогается. Чужая ссылка получает ответ «эту ссылку приложение не запрашивало…, введите код из письма» — в
каждом письме есть код, поэтому после перезапуска приложения пользователь не теряет вход. Тесты:
`cloud::auth::tests::link_not_requested_by_this_app_is_refused_and_keeps_current_session` и ещё четыре.

Дальше (по желанию): перейти на PKCE-поток Supabase (`code_challenge` в `/signup` и `/recover`, обмен `?code=` на
сессию), как уже сделано для облачных дисков (`drives.rs`). Тогда в ссылке не будет токенов совсем.

### H2. Нет двухфакторной аутентификации

В `cloud/auth.rs` нет ни одного вызова `/factors`, на рабочем проекте `auth.mfa_factors` пуст. Для CRM с базой
клиентов это главный пробел: пароль — единственный барьер, а `delete-account` и смена почты защищены только им.

Ответ на вопрос Maksim «если только в Pro, можно ли бесплатно»: **TOTP (приложение-аутентификатор: Google
Authenticator, 1Password, Яндекс Ключ) в Supabase бесплатен на всех тарифах** и включён по умолчанию. Платный
только MFA по SMS/WhatsApp ($75 в месяц, только Pro+; https://supabase.com/docs/guides/platform/manage-your-usage/advanced-mfa-phone).
Сторонний сервис не нужен. План для пакета:

1. Настройки → Безопасность: «Включить вход с кодом» — `POST /auth/v1/factors` (type `totp`) → QR и секрет →
   `POST /factors/{id}/challenge` + `/verify`; 10 одноразовых резервных кодов (хранить их хеши можно в
   `user_settings` или в отдельной таблице — это миграция, нужно «да»).
2. Вход: после пароля, если `aal1` и есть фактор, — экран кода, `challenge`/`verify` → `aal2`.
3. Сервер: для управляющих действий требовать `aal2`, когда у пользователя есть фактор —
   `(auth.jwt() ->> 'aal') = 'aal2'` в `private.require_perm` для `members.manage`, `roles.manage`,
   `workspace.delete`, `export` и в `delete-account` (проверка `amr` уже есть). Владелец Workspace может
   включить «2FA обязательна для всех участников».
4. Восстановление при потере телефона — резервный код или поддержка (`admin` удаляет фактор), с письмом
   владельцу аккаунта.

### H3. Журнал конфликтов открывает поля скрытых записей (исправлено)

`supabase/migrations/20261121120000_team_access_fixes.sql:449` — политика `sync_conflicts_select` проверяла только
`records.view`. В `sync_conflicts` лежат значения полей `kept`/`lost` любой записи
(`20261110120100_crm_core.sql:559–582`). Сотрудник с областью «свой отдел» или «только свои» (ADR-096) прямым
`GET /rest/v1/sync_conflicts?workspace_id=eq.<ws>` получал названия компаний, суммы сделок, телефоны и прочие поля
записей, которые ему не показываются.

Исправление: миграция `20261122140000_scope_leak_fixes.sql` — функция `private.row_visible(table, id)`
(SECURITY INVOKER, таблица только из реестра `private.crm_entities`) проверяет строку теми же политиками RLS, что и
обычное чтение; политика журнала требует её. Тест `supabase/tests/test_scope_leaks.py`.

### M1. Карточки CRM в чате обходят видимость (исправлено)

`20261111090000_chat_live_attachments.sql:87` — `chat_attachment_view` показывала название и подпись (у сделки —
сумму) всем участникам обсуждения с `records.view`, без области роли и отдела. `chat_attachments` (стр. 50–68)
позволяла прикрепить запись, которую автор не видит, а по ответу — проверить, существует ли id.

Исправление в той же миграции: обе функции проверяют `private.can_see_entity` для каждой карточки; скрытая карточка
показывается как «недоступна», прикрепить её нельзя (ответ тот же, что для несуществующей).

### M2. Подлинность обновлений

`updates.rs:302–345` скачивает установщик и сверяет SHA-256 из того же релиза GitHub; macOS-пакет проверяется по
`Info.plist` (`check_bundle_info`), но не по подписи. Подпись macOS — собственный сертификат или ad-hoc
(`release.yml:79–123`), Windows-установщик не подписан. Значит, кто получил право загружать файлы в релизы
(украденный токен, сессия GitHub), ставит свой код всем пользователям при следующем автообновлении.

Рекомендация (бесплатно): подпись Ed25519 (minisign / формат Tauri updater). Закрытый ключ — секрет окружения
`production` (его видит только задача публикации после ручного подтверждения), открытый ключ вшит в приложение;
`download` отклоняет файл без верной подписи. На macOS дополнительно — `codesign --verify -R` с требованием
текущего сертификата, когда секреты `MACOS_SIGN_*` заданы. Отдельный пакет, затрагивает `release.yml`.

### M3. Пароль рабочей базы доступен любой ветке

`cloud-backup.yml` берёт `secrets.SUPABASE_DB_URL` (пароль роли `postgres`) без `environment:`. Секрет уровня
репозитория читает любой workflow, запущенный push-ем в любую ветку этого репозитория (в том числе ветки Claude).
Рекомендация для Maksim: Settings → Environments → создать `backup` с правилом «только `main`», перенести туда
`SUPABASE_DB_URL` и `BACKUP_PASSPHRASE`, в `cloud-backup.yml` добавить `environment: backup` (изменение workflow
сделаю отдельным PR по команде). То же проверить для `migrate.yml` (там окружение `database` уже есть).

### M4. Пароли

`cloud/validation.rs:16` требует 8+ символов, строчную, заглавную и цифру, но только в приложении; прямой
`POST /auth/v1/signup` их обходит, если в Dashboard не заданы требования. Advisors рабочего проекта сообщают:
Leaked password protection выключена (это функция Pro, ADR-035 — оставляем). Рекомендация для Maksim (бесплатно):
Authentication → Providers → Email → Password requirements: минимум 10, «строчные, заглавные, цифры»; Minimum
password length 10. Я не могу проверить эти настройки только чтением.

### M5. Вебхуки маркетплейса

`_shared/netguard.ts` проверяет имя, но `fetch` разрешает его заново (DNS rebinding, известно по ADR-046). Добавлю
к принятому риску: событие с `crm.read` содержит всю строку (`to_jsonb(new)`, `marketplace.sql:351`), включая записи
скрытых отделов — это ожидаемо (ставит `workspace.manage`), но в окне установки стоит прямо писать «интеграция
получит все записи Workspace». После перехода бизнес-данных на сервер клиента маркетплейс-доставку стоит
перенести туда же.

### L1. Чтение произвольного файла через `crash_report_text` (исправлено)

`commands.rs:386` читал любой путь, переданный окном. Без XSS это не эксплуатируется (CSP `script-src 'self'`,
React без `dangerouslySetInnerHTML`), но команда теперь читает только отчёты из тех же папок, что показывает
`crash_reports`.

### L2. Резервные копии и удаление аккаунта

`cloud-backup.yml` хранит полный снимок (включая `auth`: хеши паролей, будущие секреты TOTP) 90 дней. После удаления
аккаунта его данные остаются в копиях до 90 дней. Это допустимо, если написано в политике конфиденциальности
(«удалённые данные исчезают из резервных копий в течение 90 дней»). Для 152-ФЗ/GDPR стоит добавить этот срок в wiki.

### L3. Ai и текст с сайтов

Лиды приходят с чужих сайтов, их текст попадает модели. Удаление и отправка наружу подтверждаются всегда
(`lib/aiTools.ts:74`), но в режиме «Безопасное — без вопросов» модель может без вопроса менять ответственного,
создавать задачи и заметки по указанию, спрятанному в описании лида. Рекомендация: в этом режиме не выполнять без
вопроса `write`-инструменты в том же ходе, где модель читала содержимое лидов.

## Проверено и в порядке

* **Межарендная изоляция.** Все таблицы `public` с `enable` + `force` RLS; у `anon` нет прав на таблицы и ни на
  одну definer-функцию (запрос к рабочему проекту: 0); все definer-функции в миграциях с `set search_path = ''`; автотест
  ADR-046 требует проверки вызывающего. Приглашения: токен 256 бит, хранится хеш, принимается только на свою
  подтверждённую почту.
* **Секреты на устройстве.** Сессия, ключи SQLCipher, токены интеграций — Keychain/DPAPI (`secrets.rs`);
  SQLCipher-база, `PRAGMA key` после проверки `cipher_version` (`db.rs:118–130`); в приложении только публичный ключ
  Supabase (`release-check`).
* **Edge Functions.** Хук писем — подпись Standard Webhooks с окном 5 минут; cron-функции и `market-relay` — секрет
  сравнением без раннего выхода; `delete-account` — проверка токена в Auth и свежий вход по паролю.
* **Облачные диски.** OAuth с PKCE (S256) и `state`, приём только на `127.0.0.1` (`drives.rs:358–483`).
* **Инъекции.** Динамический SQL в ядре — только имена из схемы (`workspace/query.rs:74`); экспорт CSV
  нейтрализует формулы (тесты `csv_neutralizes_formulas`); `open_url` — только http(s)/mailto/tel.
* **Окно приложения.** CSP без `unsafe-eval`, `withGlobalTauri: false`, минимальные права окна.
* **PayPal.** В `main` платёжного кода нет. Заготовка (патч в файлах проекта) проверяет подпись вебхука через
  PayPal и перечитывает заказ, сумму берёт из базы — так и нужно.
* **Зависимости.** `cargo audit` — 0 уязвимостей, `npm audit --omit=dev` — 0; `cargo deny` в CI.

## Что изменится с новым размещением данных (ADR-098)

Когда бизнес-данные уйдут на сервер клиента, общий Supabase хранит только учётные записи — поверхность атаки
резко меньше, но появляются новые обязанности. Их стоит заложить в пакеты K3/K4:

1. **Сервер клиента** (Hetzner и др.): ставить только с файрволом (открыты 443 и 22 по ключу), автоматические
   обновления ОС, TLS (Let's Encrypt), Postgres не наружу, ежедневная зашифрованная копия в хранилище клиента.
   Ключи `service_role` клиента — только на его сервере и в Keychain администратора, не в приложении сотрудников.
2. **Свой Supabase клиента**: тот же набор миграций с RLS — наши тесты `supabase/tests` должны прогоняться и для
   схемы, которую ставит приложение.
3. **Локальная сеть**: сервер в LAN всё равно с TLS и паролем; не открывать Postgres всем в сети.
4. **Вход**: общий аккаунт Customers не должен давать доступ к базе клиента сам по себе — сервер клиента проверяет
   JWT (подпись общего проекта, `aud`, `aal2` для администраторов), а не доверяет приложению.
