# Синхронизация и офлайн-режим

Статус: синхронизация **лидов** одного пользователя между устройствами — **реализовано** (docs/cloud.md);
синхронизация **CRM** Workspace между пользователями — **запланировано** (этап 3). CRM повторяет проверенную
схему лидов и добавляет то, чего ей не хватает для нескольких людей.

## 1. Что уже работает (генератор лидов)

* Изменение пишется в локальную базу и журнал `sync_dirty` в одной транзакции (нельзя потерять при сбое).
* Выгрузка: `sync_push` пакетами до 500 изменений; поле применяется, только если его время (`field_ts`) новее
  серверного; время с устройства не может быть больше времени сервера.
* Загрузка: `GET …?server_seq=gt.<курсор>&order=server_seq&limit=…` по каждой таблице; курсор двигается в той же
  транзакции, что и применение данных.
* Удаление — надгробие `deleted = true`.

## 2. CRM: протокол

### 2.1 Локальная очередь

Каждое изменение на устройстве — **операция** в `sync_outbox` той же транзакцией, что и изменение записи:

```json
{ "op_id": "1f6c…",              // UUID, создаётся один раз; повтор отправки — тот же op_id
  "entity": "deals", "id": "9a2e…",
  "kind": "upsert",             // upsert | delete | restore | archive | unarchive | link | unlink | move_stage
  "fields": { "amount": 150000, "stage_id": "…" },
  "ts": { "amount": "2026-11-12T10:00:01.120Z", "stage_id": "2026-11-12T10:00:01.120Z" },
  "base_version": 7 }            // version строки, на которой основано изменение
```

Несколько правок одной записи до отправки сливаются в одну операцию (последнее значение поля, его время).

### 2.2 Выгрузка: `crm_push(p_workspace, p_device, p_ops)` (security invoker, RLS действует)

Для каждой операции:

1. `sync_ops` уже содержит `op_id` → вернуть сохранённый результат (идемпотентность; повтор после обрыва связи
   ничего не дублирует).
2. Проверить разрешение (`records.create` / `records.edit` или `edit_own` / `records.delete`).
3. Слить по полям: поле применяется, если `ts` > `field_ts[поле]` сервера (`ts` ограничено `now()`).
4. **Конфликт** — когда `base_version` < текущей `version` **и** серверное поле изменено после версии, на которой
   основана операция (`field_ts[поле] > ts_базы`). Тогда сохраняется более позднее значение, проигравшее
   пишется в `sync_conflicts` (кто, что, когда) — пользователь видит отметку «Изменено одновременно с …» и может
   вернуть своё значение одним нажатием. Ничего не теряется молча.
5. Записать `sync_ops(op_id, result)`.

До 500 операций за вызов; ответ: `{server_time, results: [{op_id, status: applied|merged|conflict|rejected, version}]}`.

### 2.3 Почему не «последняя запись выигрывает» целиком

| Данные | Стратегия | Почему |
|---|---|---|
| Скалярные поля (название, сумма, ответственный, этап) | слияние по полям + журнал конфликтов | правки разных полей разными людьми не мешают друг другу; одновременная правка одного поля видна |
| Связи «многие ко многим» (контакты сделки, метки) | строки-связи (`deal_contacts`) с надгробием; `link`/`unlink` | добавление контакта одним и другого контакта другим сохраняет оба (LWW над массивом потерял бы одно) |
| Текст (заметки, комментарии) | новая строка на каждую заметку/комментарий; правка — поле `body` с конфликтом | двое пишут заметки — обе остаются |
| История (этапы сделки, активности, аудит) | только добавление | порядок по `server_seq`, ничего не перезаписывается |
| Удаление | `deleted_at` со своим временем; правка удалённой записи её не воскрешает, а пишется в `sync_conflicts` | повторная синхронизация старого устройства не может ни удалить свежую запись, ни вернуть удалённую |
| Порядок этапов и коллекций | `position numeric` (дробная вставка) | перестановки разных элементов не конфликтуют |

**Устаревший повтор**: у старой операции время полей меньше серверного, поэтому она не перезапишет более свежие
изменения другого пользователя; `op_id` не даст применить её дважды.

### 2.4 Загрузка

Как у лидов: по каждой таблице `?workspace_id=eq.<ws>&server_seq=gt.<курсор>&order=server_seq.asc&limit=500`.
Строки с `deleted_at` применяются как надгробия. Локальные поля с неотправленными операциями не затираются:
сервер сравнивает `ts`, а клиент повторно применяет свои ожидающие операции поверх загруженной строки.

### 2.5 Realtime

* Приватный канал `ws:<workspace_id>`; авторизация — политика на `realtime.messages`: участник с `records.view`.
* Триггер после записи отправляет `realtime.send({table, server_seq}, 'changed', 'ws:<id>', true)` — без данных.
* Клиент на «звонок» запускает загрузку с курсором (с задержкой 300 мс, чтобы пачку изменений забрать одним запросом).
* Presence в том же канале — список «в сети» для аватаров.
* Без Realtime (нет сети, лимит): загрузка при запуске, при возвращении окна в фокус, после выгрузки и не чаще
  раза в 5 минут, пока окно активно. Постоянного опроса нет.

## 3. Офлайн и восстановление

* Запись — всегда в локальную базу; интерфейс не ждёт сети. Статус записи: `synced` / `pending` / `conflict` / `rejected`.
* Повторы: экспоненциальная пауза 2 с → 5 мин с разбросом ±20 %; при восстановлении сети — сразу.
* Ошибка прав (`42501`) — операция `rejected`: запись возвращается к серверной версии, пользователь получает
  объяснение; ошибка данных (`22023`) — то же с текстом проверки.
* Сбой приложения: очередь и курсоры в SQLite (WAL), поэтому после перезапуска отправка продолжается с тех же
  `op_id`. Операция удаляется из очереди только после ответа сервера.
* Выход из Workspace или удаление участника: неотправленные операции показываются списком с выгрузкой в файл
  перед удалением локальной базы Workspace.

## 4. Бережное отношение к бесплатным лимитам

* Пакеты до 500 операций/строк; слияние нескольких правок одной записи до отправки.
* Один канал Realtime на активный Workspace, сообщения — только номер изменения.
* Загрузка только по курсору (индекс `(workspace_id, server_seq)`), без полных выгрузок.
* Очистка: `sync_ops` старше 30 дней, надгробия старше 90 дней — функция `private.crm_maintenance()` по
  расписанию `pg_cron` (расширение включается в проекте; если оно выключено, ту же функцию раз в сутки вызывает
  устройство owner/admin через RPC, повтор безопасен).
