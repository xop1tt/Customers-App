# CRM: модель данных и поведение

Статус: этапы 3–7 **реализованы** (см. отличия в §9); пользовательские поля, вложения (до 5 МБ, содержимое в базе, не в Storage), присутствие (опрос раз в 25 с), редакторы воронок и ролей и загрузка локального Workspace в облако — **реализованы** (миграции `20261110130000…130300`); аналитика — **запланирована**. Документ — контракт для реализации; таблицы и столбцы подробно — в
[DATABASE_SCHEMA.md](DATABASE_SCHEMA.md), права — в [WORKSPACE_AND_PERMISSIONS.md](WORKSPACE_AND_PERMISSIONS.md).

## 1. ER-модель

```
auth.users 1─1 user_profiles
auth.users 1─* workspace_members *─1 workspaces 1─* workspace_invitations
                     │ *                    │
                     └─1 roles *─* permissions (role_permissions)
                                            │ workspace_id во всех строках ниже
 ┌──────────────────────────────────────────┴───────────────────────────────────────────┐
 │ companies 1─* contacts            crm_leads ──(converted_to)──► companies / contacts │
 │     │1            │*                  │                                              │
 │     *             *                   │                                              │
 │   deals *─* contacts (deal_contacts)  │      pipelines 1─* pipeline_stages           │
 │     │ *─1 pipelines, *─1 pipeline_stages, 1─* deal_stage_history                    │
 │                                                                                      │
 │ tasks ─┐                                                                             │
 │ activities ─┼─ entity_type + entity_id → companies | contacts | crm_leads | deals    │
 │ notes ─┤       (полиморфная ссылка, workspace совпадает — проверяет триггер)         │
 │ comments ─┤                                                                          │
 │ attachments ─┘ (файл в Storage: attachments/<workspace_id>/<uuid>)                   │
 │                                                                                      │
 │ custom_fields 1─* custom_field_values (entity_type + entity_id)                      │
 │ collections (личные / общие) 1─* collection_user_prefs (порядок в меню у каждого)    │
 │ audit_log (только добавление) · sync_ops (идемпотентность) · sync_conflicts          │
 └──────────────────────────────────────────────────────────────────────────────────────┘
генератор лидов (отдельно, по user_id): leads · exclusions · user_settings
```

## 2. Общие правила всех CRM-сущностей

Каждая строка имеет:

| Столбец | Смысл |
|---|---|
| `id uuid` | создаётся на устройстве (UUID v4) — запись появляется офлайн без обращения к серверу |
| `workspace_id uuid not null` | владелец данных; не меняется (триггер) |
| `created_by`, `created_at` | автор; ставит сервер (`auth.uid()`, `now()`), клиентские значения игнорируются |
| `updated_by`, `updated_at` | последний автор изменения |
| `owner_id` | ответственный (участник Workspace), там, где это имеет смысл |
| `archived_at` | архив: запись скрыта из обычных списков, но доступна поиском и в карточках |
| `deleted_at` | мягкое удаление (надгробие); физически строки удаляет только очистка через 90 дней |
| `version bigint` | номер версии строки, +1 при каждом изменении |
| `field_ts jsonb` | время последнего изменения каждого поля (слияние, см. SYNC_ARCHITECTURE.md) |
| `server_seq bigint` | порядок изменений для курсоров синхронизации |

Каждое изменение записывается в `activities` (тип `system`) соответствующей карточки и, если оно важное
(удаление, смена ответственного, смена роли, экспорт), — в `audit_log`.

## 3. Клиенты, компании, контакты

* **crm_leads** — потенциальный клиент до квалификации: имя, компания (текстом), телефоны, почты, источник,
  статус (`new`, `in_progress`, `qualified`, `disqualified`, `converted`), ответственный. Генератор лидов сюда
  не пишет сам: только по команде пользователя.
* **companies** — организация: название, ИНН/рег. номер, домен, сайт, телефоны, почты, адрес, отрасль, размер.
* **contacts** — человек: имя, фамилия, должность, телефоны, почты, мессенджеры; `company_id` — необязательно.
  У компании много контактов; контакт может быть без компании.
* У клиента (компании или контакта) много сделок; у сделки одна компания и много контактов (`deal_contacts`).

### Дедупликация

Ключи сравнения (нормализованные, хранятся в столбцах `dedupe_keys text[]` с GIN-индексом):

| Сущность | Ключи |
|---|---|
| companies | `domain:` домен сайта или почты (кроме бесплатных почт), `inn:` ИНН, `phone:` телефон E.164, `name:` нормализованное название + город |
| contacts | `email:` почта, `phone:` телефон E.164, `name:` имя + company_id |

Создание и импорт показывают совпадения до сохранения («Похоже на: …»), объединение — отдельная операция
`merge_records(target, source)` (переносит связи, сохраняет историю, источник получает надгробие).

## 4. Преобразование найденного лида

Команда `convert_lead(lead_id, workspace_id, options)` (этап 4):

1. Берёт лид генератора (`public.leads` пользователя или локальную базу) — сам лид не меняется, только
   получает отметку `data.crm = {workspace_id, company_id, contact_id, converted_at}` (поле `data` уже синхронизируется).
2. По ключам дедупликации ищет существующие компанию и контакт в Workspace; найденные — переиспользуются.
3. Создаёт `companies` (название, сайт, телефоны, почты, адрес, категории → поле «Отрасль»/метки) и `contacts`
   (если у лида есть человек), сохраняет исходник целиком в `source_payload jsonb` и `source = 'leadgen:<источник>'`,
   `source_lead_id`.
4. Заметку лида переносит в `notes` новой карточки, добавляет активность `system: converted`.
5. По желанию создаёт сделку в выбранной воронке.

Повторный вызов с тем же лидом не создаёт дубликатов: уникальный индекс `(workspace_id, source_lead_id)` у
companies и contacts, операция идемпотентна по `op_id`. Генератор лидов работает без этой команды.

## 5. Сделки и воронки

* `pipelines` — несколько воронок; у каждой упорядоченные `pipeline_stages` (`position`, `color`, `probability` 0–100,
  `kind`: `open`, `won`, `lost`). Шаблон при создании Workspace: Новый лид → Первый контакт → Переговоры →
  Подготовка предложения → Согласование → Успешная сделка (won) → Проигранная сделка (lost). Шаблон — только начальные строки.
* Порядок этапов — `position numeric` (вставка между соседями без перенумерации; раз в N вставок сервер
  нормализует). Удаление этапа с сделками требует указать этап, куда их перенести (RPC `delete_stage(stage, move_to)`).
* `deals`: название, `amount numeric(18,2)`, `currency char(3)` (ISO 4217), `expected_close_date`, `owner_id`,
  `company_id`, `status` (`open`, `won`, `lost`, вычисляется из `kind` этапа), `lost_reason`, `closed_at`.
* Каждое перемещение — строка `deal_stage_history` (from, to, кто, когда) — только добавление; триггер пишет её
  на сервере при изменении `stage_id`, поэтому история не зависит от клиента.

## 6. Задачи и история взаимодействий

* `tasks`: название, описание, `assignee_id`, `created_by`, `due_at`, `remind_at`, `priority` (`low`, `normal`,
  `high`, `urgent`), `status` (`todo`, `in_progress`, `done`, `cancelled`), `completed_at`, связь с сущностью.
* `activities` — лента карточки: `type` (`call`, `email`, `meeting`, `follow_up`, `reminder`, `agreement`, `payment`,
  `custom`, `system`), `occurred_at`, `author_id`, `summary`, `payload jsonb`, связь с сущностью. Задачи, заметки,
  комментарии и системные события показываются в той же ленте.
* `notes`, `comments` (ветки через `parent_id`), `attachments` (метаданные; файл в приватном бакете Storage).
* Связь с сущностью — `entity_type` (`company`, `contact`, `crm_lead`, `deal`) + `entity_id`. Триггер проверяет,
  что сущность существует и в том же Workspace (иначе через ссылку можно было бы прочитать чужие данные).

## 7. Пользовательские поля и коллекции

* `custom_fields`: `entity_type`, `key` (`^[a-z][a-z0-9_]{0,40}$`, уникален в Workspace+entity), `label`, `type`
  (`text`, `textarea`, `number`, `money`, `date`, `datetime`, `boolean`, `select`, `multiselect`, `url`, `email`,
  `phone`), `options jsonb` (варианты, валюта), `validation jsonb` (min/max/regex/required), `position`, `archived_at`.
* `custom_field_values`: одна строка на (поле, запись) с типизированными столбцами `value_text`, `value_number`,
  `value_date`, `value_ts`, `value_bool`, `value_json`. Частичные индексы: `(field_id, value_number) where value_number is not null`
  и т. д. Проверку типа и `validation` делает триггер на сервере и та же функция в Rust офлайн.
* **Коллекции** — сохранённые представления: `entity_type`, `name`, `icon`/`emoji`, `visibility` (`private` — видна
  автору; `workspace` — всем с `records.view`, менять может автор или `collections.manage`), `config jsonb`:
  `{ "filters": [{"field": "owner_id", "op": "eq", "value": "$me"}], "sort": [{"field": "updated_at", "dir": "desc"}],
  "columns": ["name", "owner_id", "cf:budget"], "widths": {...} }`. Фильтр исполняется запросом к таблице (локально — SQL
  к базе Workspace), данные не копируются. Порядок в левой панели у каждого свой (`collection_user_prefs`).
* Встроенные коллекции создаются как обычные строки шаблона: Все клиенты, Мои клиенты, Новые лиды, Сделки на этой
  неделе, Просроченные задачи, Успешные сделки, Потерянные сделки.

## 8. Дизайн-предложение: три элемента интерфейса

Компоновка, навигация и тема Flat Dark не меняются. Новые панели, кнопки и меню, кроме перечисленного, не добавляются.

### 8.1 Аватары сотрудников (верхняя панель, справа)

* Место: `TopBar`, правая часть, **между** чипом синхронизации и кнопкой «Найти лиды» (кнопка панели сведений
  остаётся последней, у края, как сейчас).
* Вид: до 4 аватаров 24×24 px с наложением −6 px и обводкой цвета фона 2 px; дальше чип «+N» того же размера.
  Источник — `user_profiles.avatar_path` (Storage) или инициалы (существующий `Avatar` из `ui/kit`). Точка присутствия
  8 px (Realtime Presence по каналу Workspace): зелёная — в сети, без точки — нет.
* Нажатие открывает существующий `Popover`: список участников (аватар, имя, роль, «в сети / был …»),
  внизу кнопка «Пригласить» — только при разрешении `invitations.manage`.
* Не показывается у локальной учётной записи и в Workspace из одного человека (нечего показывать).
* Узкое окно (< 1100 px логических): один аватар + «+N». Размеры в CSS-пикселях, поэтому масштаб Windows
  125–200 % и Retina не ломают раскладку; проверяется снимками этапа 2 (`npm run shots`).

### 8.2 Крупная иконка раздела

* Место: `topbar-title`, слева от `h2` (там же, где сейчас название раздела), 22 px, выравнивание по базовой линии.
* Разделы CRM: 🤝 Клиенты, 🏢 Компании, 👤 Контакты, 💼 Сделки, 📋 Задачи, 📊 Аналитика; генератор: 🔎 Поиск лидов.
  Существующие разделы генератора сохраняют свои иконки в левой панели; в заголовке у них тоже появляется эмодзи из
  таблицы `SECTIONS` (одно новое поле `emoji`).
* Коллекция показывает свою иконку/эмодзи; выбор — в диалоге создания/переименования коллекции (сетка из 48 эмодзи
  + 24 иконки кита, без внешних библиотек).

### 8.3 «Коллекции» в левой панели

* Место: новая группа `nav-group` в `Sidebar` **после** основной и рабочей групп и **перед** группой источников.
* Заголовок группы «Коллекции» с кнопкой «+» (создать) справа — так же, как выглядят заголовки других групп.
* Строки как `NavItem`: эмодзи, название, счётчик (если включены счётчики панели). Порядок меняется тем же
  перетаскиванием, что уже есть в режиме «Настроить панель» (`sidebarOrder` → `collection_user_prefs.position`).
* Контекстное меню строки (существующий `showMenu`): Переименовать, Иконка, Сделать общей/личной, Удалить —
  пункты видны по правам.
* Группа скрывается, если коллекций нет и Workspace не выбран (генератор лидов без CRM выглядит как сейчас).

## 9. Отличия реализации (этапы 4–7)

* Разделы CRM открываются через коллекции: семь встроенных (Все клиенты, Мои клиенты, Новые лиды, Сделки на этой
  неделе, Просроченные задачи, Успешные и Потерянные сделки) и свои (кнопка «+»). Отдельных пунктов «Компании»,
  «Контакты» в левой панели нет — это были бы новые элементы сверх трёх разрешённых.
* Карточка записи открывается в панели сведений (там же, где сведения о лиде): поля, связанные записи, лента
  (заметки, события, комментарии), задачи, этапы сделки, конфликты.
* Группа «Коллекции» стоит сразу после основной группы и перед «По источнику» (в текущей панели группа «Работа» идёт
  после источников, поэтому «после рабочей группы» и «перед источниками» одновременно выполнить нельзя).
* Аватары: без точки присутствия (Realtime Presence — запланировано); пункт «Рабочее пространство» добавлен в
  существующее меню учётной записи, чтобы окно Workspace было доступно и без аватаров (локальная учётная запись,
  Workspace из одного человека).
* Иконка коллекции — только эмодзи из 48; 24 иконки кита — запланировано.
* Порядок коллекций — личный (`collection_user_prefs`), меняется перетаскиванием в режиме «Настроить панель».
* Вложения (Storage) — не реализованы: на стенде CI нет Storage, проверить нечем.
