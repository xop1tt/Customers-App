## 1. Executive Summary

### 1.1. Общее состояние

Интерфейс Customers уже собран по единой системе: один набор компонентов (`ui/kit.tsx`, `ui/overlay.tsx`), токены в `styles/tokens.css`, тёмная и светлая темы, русский и английский языки, клавиатурная поддержка у списков и меню, `aria`-атрибуты на основных элементах, подтверждения для опасных действий (24 вызова `confirmDialog`, все деструктивные — с красной кнопкой), понятные пустые состояния. Для бесплатного приложения от одного разработчика это сильная основа.

До уровня корпоративной CRM его отделяют не «красота», а пять системных вещей. Каждая подтверждена кодом или измерением.

1. **Названия не образуют единого языка (F-01…F-12).** Одно понятие называется по-разному, а разные понятия — одинаково. «Отчёты» — это и аналитика воронки, и страница диагностики в настройках. «Лиды» — это и найденные поиском заказчики, и записи CRM («Лиды CRM»). Результат сделки: «Успешна», «Выиграна» и «Выиграно» в трёх местах. «Workspace» и «Рабочее пространство» встречаются рядом.
2. **У экрана нет одного главного действия (F-13…F-17).** Кнопка «Найти лиды» (primary) стоит в верхней панели **каждого** экрана, включая CRM. На «Сегодня» рядом с ней стоит ещё одна primary-кнопка «Новая сделка» (скриншот демо). Три разные кнопки значат «перенести» (`Перенести…`), и три кнопки «Открыть» ведут в три разных диалога.
3. **Контраст и цвет не доведены до нормы (F-18…F-25).** Третичный текст (подсказки, плейсхолдеры, счётчики) имеет контраст 3.2–3.8 : 1 вместо 4.5 : 1; текст на основной кнопке — 3.20 : 1; в светлой теме ссылки акцентного цвета — 2.96 : 1; рамки полей ввода — 1.6 : 1 вместо 3 : 1. Автотест доступности явно отключает проверку контраста (`app/a11y.test.tsx:16`), поэтому ни CI, ни разработчик этого не видят.
4. **Эмодзи вместо системы иконок (F-25).** Заголовки экранов, типы записей и коллекции используют цветные эмодзи (`lib/leads.ts` `SECTIONS.*.emoji`, `lib/crm.ts` `ENTITIES.*.emoji`, `COLLECTION_EMOJI`). Они противоречат целевому направлению «сдержанный, монохромный Enterprise»; на macOS и Windows рисуются разными системными шрифтами (**?** на устройстве).
5. **Сложные задачи спрятаны глубже, чем нужно (F-26…F-35).** Управление участниками, ролями, воронками и полями живёт в одном диалоге «Рабочее пространство», который открывается из меню аккаунта. Журнала действий в интерфейсе нет, хотя право `audit.view` и таблица `audit_log` существуют. Сообщения обещают «корзину Workspace», но экрана корзины нет. Запись CRM — только в правой панели шириной 300–640 px, без полноэкранной карточки.

### 1.3. Потенциал улучшения

Из 33 подтверждённых недостатков (§§3–9) 21 исправляется **без изменения поведения**: переименованием, заменой токенов, перестановкой кнопок и заменой эмодзи на иконки. Они укладываются в этап 3 (только приложение, без базы). Ещё 7 требуют новых макетов (по правилу CLAUDE.md §7 «сначала макеты на согласование»). 5 — функциональные пробелы, которые упираются в изменения базы и вынесены в отдельный документ.

Оценка достигнутого эффекта до реализации не даётся: у проекта нет метрик использования, а их выдумывание противоречит условиям задачи.

### 1.4. Главные рекомендации в одном абзаце

(1) Принять словарь терминов (§4) и применить его сквозным проходом вместе с `i18n.en.ts`. (2) Ввести правило «один экран — одно главное действие» и убрать глобальную «Найти лиды» из верхней панели вне модуля поиска. (3) Заменить токены контраста и добавить в тесты проверку контраста по таблице токенов, не отключая существующие тесты. (4) Заменить эмодзи на монохромные иконки и сделать акцент монохромным (основная кнопка — инверсия нейтрального цвета, синий остаётся только у ссылок, фокуса и выделения). (5) Вынести «Участники и роли» и «Воронки и поля» из диалога в раздел «Администрирование» настроек, добавить экран журнала действий только после решения Maksim по базе. (6) Дать записи CRM полноэкранный режим, оставив правую панель необязательной.

### 2.2. UX-принципы (не продуктовые, а исследовательские)

| Источник | Вывод, на который опирается отчёт |
|---|---|
| NN/g, «Maintain Consistency and Adhere to Standards» | Пользователь не должен гадать, значат ли разные слова одно и то же; нужна внутренняя и внешняя согласованность. → §4, F-01…F-12. |
| NN/g, «Confirmation Dialogs Can Prevent User Errors» | Подтверждение уместно для серьёзных необратимых действий, но злоупотребление приводит к автоматическому «да». → §8: у Customers 24 подтверждения, часть для обратимых действий (R-24). |
| NN/g, «Cancel vs Close» | Крестик без подписи неоднозначен; лучше текстовые подписи и «закрыть и сохранить». → F-14. |
| NN/g, «Icon Usability» | У большинства иконок нет единого смысла, нужны текстовые подписи. → иконки-кнопки без подписи (F-22). |
| NN/g, «Dangerous UX: Consequential Options Close to Benign Options» | Опасные и безопасные действия разносить и различать несколькими признаками. → `BulkBar`: «Исключить» и «Удалить» стоят рядом с «Экспорт» (F-15). |
| NN/g, «Data Tables: Four Major User Tasks» | Таблица должна поддерживать поиск записей по условию, сравнение, правку строки и действия над записью. → таблицы CRM (F-30, F-31). |
| NN/g, «Designing Empty States in Complex Applications» | Пустое состояние сообщает статус, обучает и ведёт к ключевому действию. → большинство состояний Customers выполнены верно; пробелы в §8. |
| NN/g, «Indicators, Validations, and Notifications» | Выбор между индикатором, валидацией и уведомлением зависит от срочности и необходимости действия. → правила уведомлений §10.11. |
| W3C WCAG 2.2, SC 2.5.8 «Target Size (Minimum)» | Цель указателя не меньше 24×24 CSS px либо достаточные интервалы. → размеры кнопок §7.5. |
| W3C WCAG 2.2, SC 1.4.11 «Non-text Contrast» | Границы и состояния элементов управления — не менее 3 : 1 к соседнему цвету. → F-20. |
| W3C WCAG 2.2, SC 1.4.3 «Contrast (Minimum)» | Обычный текст — не менее 4.5 : 1 (значение взято из спецификации, страница в сессии не открывалась). → F-18…F-21. |

### 6.3. Предлагаемая структура (◇)

Рейка модулей остаётся: это выбор Maksim (пакет C1, вариант B), и по паттерну она совпадает с «областями» Dynamics 365 (переключатель уровня выше групп) и с боковой панелью Linear (см. §2). Меняются названия, состав групп и место администрирования.

```
Рейка (64 px)
├─ CRM
│   Работа:    Сегодня · Календарь · Сделки (доска) · Отчёты
│   Списки:    Все клиенты · Мои клиенты · Заявки · Сделки · Задачи · … свои
│              (встроенные коллекции; «Задачи» и «Сделки» — готовые коллекции, не новые функции)

│   Поиск:     Источники · Журнал поиска
│   По источнику: (как сейчас; «По оценке» уходит в фильтр списка)
├─ Чат         Чат (личные и обсуждения)
├─ Команда     Сотрудники · Входящие
```

Заголовок левой панели в CRM, «Чате» и «Команде» превращается в **переключатель рабочих пространств** (имя пространства + шеврон; список открывается как меню). Образец — переключатель областей в Dynamics 365 и переключатель приложений в Salesforce (§2). Пока доступно одно пространство, это просто название.

**Окно «Настройки»** (категории по аудитории, а не по частоте):

### 6.5. Правила для боковых панелей (кратко; полностью — §10.12)

1. Слева — навигация по разделам выбранного модуля; справа — **необязательная** панель сведений о выбранной записи (по требованию: «необязательная правая панель»).
2. Правая панель открывается выбором записи, закрывается Esc и кнопкой; когда места мало (центр < 560 px) — поверх (как сейчас `inspector float`).
3. У записи CRM есть полноэкранный режим (открыть записью на всю область) — для долгой работы, как вкладки страницы записи у HubSpot (R-17).

## 10. Предлагаемая дизайн-система «Enterprise Mono»

Статус раздела — **◇ предложение**. Ничего из него не реализовано; по CLAUDE.md §7 существенные изменения интерфейса идут через макеты на согласование (пакет C1).

### 10.1. Принципы

1. **Сдержанность.** Один акцентный цвет только для действия и выбора; всё остальное — нейтральные серые.
2. **Монохром как данность.** Статус — форма и подпись, цвет — вторичный сигнал (не передавать смысл только цветом, WCAG 1.4.1).
3. **Плотность по выбору.** Три плотности строк: Compact 32 / Default 40 / Comfortable 48 px (сейчас фиксированные 44).
4. **Один язык.** Словарь из §4.2 и правила именования кнопок из §5 — часть системы.
5. **Совместимость.** Остаются Flat Dark, токены, русский ключ перевода; ничего, что противоречит ADR-039 (без AI) и CLAUDE.md §7.

### 10.2. Цвет — роли вместо оттенков

Предлагаемый набор семантических токенов (значения — ориентир, перед принятием проверяются скриптом контраста; существующие имена остаются как алиасы на время миграции):

| Роль | Токен | Тёмная (ориентир) | Светлая (ориентир) | Требование |
|---|---|---|---|---|
| Фоны | `--surface-0…3` (app, panel, raised, overlay) | `#141518 / #191a1e / #1f2024 / #25262b` | `#f6f6f7 / #efeff1 / #ffffff / #ffffff` | шаг 1.1–1.2 : 1 между уровнями |
| Текст | `--fg-1 / --fg-2 / --fg-3` | `#ececef / #a8a9b2 / #8b8c96` | `#1b1c20 / #4a4d57 / #636673` | **все ≥ 4.5 : 1 на всех поверхностях** (исправляет F-18) |
| Граница | `--border-subtle / --border-control` | `#2b2c33 / #6b6d78` | `#dcdfe6 / #80848f` | `border-control` ≥ 3 : 1 (исправляет F-21) |
| Действие | `--action` (кнопка), `--action-fg` | `#4c8dff` + текст `#0d1117` | `#2563eb` + текст `#ffffff` | текст на кнопке ≥ 4.5 : 1 (исправляет F-19) |
| Ссылка / фокус | `--link`, `--focus-ring` | `#6aa0ff`, `#6aa0ff` | `#1d4ed8`, `#1d4ed8` | ≥ 4.5 : 1 / ≥ 3 : 1 в обеих темах |
| Статусы | `--ok / --warn / --danger / --info` (+ фон, рамка) | как сейчас, текст на фоне ≥ 4.5 | затемнённые на 10–15 % | исправляет F-20 |
| Нейтральный тег | `--tag-neutral` | серый | серый | по умолчанию все теги серые, цвет — только у статусов |

Принципы: акцент не используется для декоративных элементов и непрочитанных счётчиков (для них — нейтральный инвертированный чип); цвета этапов воронки берутся из 8 нейтрально-приглушённых токенов, а не из палитры Tailwind (F-23).

### 10.3. Типографика

Одна гарнитура (Inter, как сейчас). Шкала: 11 / 12 / **13 (базовый)** / 15 / 20 / 26; насыщенность — только 400, 500, 600; заголовок страницы — `h1`; убрать значения 10, 12.5, 14, 16, 17, 18, 22, 38 вне шкалы (F-24). Цифры в таблицах и суммах — табличные (`.num`, уже есть).

### 10.4. Отступы, радиусы, плотность

Шкала `--sp-1…8` = 4/8/12/16/20/24/32/40. Радиусы: 3 / 5 / 8 (три вместо четырёх плюс литералов). Высоты: `--ctl-h` 28 (compact) / 32; `--row-h` 32 / 40 / 48 по настройке «Плотность таблиц».

### 10.5. Иконки

Сохранить текущий линейный набор (≈ 77). Заменить эмодзи в заголовках, типах записей и встроенных коллекциях линейными иконками (F-25); пользовательский выбор значка коллекции оставить, но предложить набор линейных иконок вместо 48 эмодзи. Один размер в контексте: 16 px в кнопках и меню, 18 px в рейке, 14 px в тегах. Каждой иконке — одно значение (устранить F-16).

### 10.6. Кнопки (единое правило)

| Вид | Когда | Оформление |
|---|---|---|
| Primary | **одно** главное действие экрана или диалога | заливка `--action` |
| Default | остальные действия | рамка `--border-control`, прозрачный фон |
| Ghost | «Отмена», «Закрыть», третичные | без рамки |
| Danger | необратимое | рамка/текст `--danger`; в подтверждении — заливка |
| Link | переход внутри текста | настоящий `<a href>` или `<button class="link">` (F-37) |

Правила: «Отмена»/«Закрыть» — всегда ghost (F-14); в диалогах подтверждение справа, отмена слева; опасное отделено от обычного (F-15); название кнопки — глагол + объект («Создать сделку», «Добавить контакт»), см. §4.2; кнопка в состоянии загрузки показывает текст действия и спиннер, а не пустое место (§5.4).

### 10.7. Таблицы и списки

Единый компонент `DataTable`: заголовок со сортировкой, выбор строк (чекбокс), панель массовых действий (как `BulkBar` у лидов), меню столбцов, контекстное меню строки, виртуализация, плотность — закрывает F-30 и сводит три реализации таблицы (§7.7) к одной. Пустое состояние: иконка + одна фраза + одно главное действие.

### 10.8. Формы и диалоги

Поля с видимой рамкой ≥ 3 : 1; подпись над полем; ошибка под полем с иконкой и текстом (не только цветом); обязательность — слово «обязательно» в подписи, а не только звёздочка. Диалоги: три размера (440 / 560 / 720); заголовок — действие («Объединить компании»), а не имя компонента. Автосохранение допустимо при видимом индикаторе «Сохранено» (F-31).

### 10.9. Обратная связь

Тост 4 с для успеха, 7 с и «закрыть» для ошибки (как сейчас — оставить); ошибки загрузки — на месте блока с кнопкой «Повторить» (проверено: `EmptyState` с `alert`, повтор **?** не везде); долгие операции — прогресс. Для `prefers-reduced-motion` отключить переходы длиннее 120 мс (F-38).

### 10.10. Состояния компонентов

Для каждого интерактивного: default / hover / active / focus-visible / disabled / loading / selected / error. Сейчас по §5.4 набор у разных кнопок разный. Фокус — кольцо 2 px `--focus-ring` с зазором, видимое в обеих темах.

### 10.11. Доступность (минимум системы)

Контраст — по таблице 10.2; фокус виден; все действия — с клавиатуры (F-37); цели ≥ 24 px (F-36); смысл не только цветом; `h1` на странице; автоматическая проверка токенов тестом контраста (F-22) — **как новый тест, существующие не ослаблять** (CLAUDE.md §5).

### 10.12. Раскладка и правая панель

Три зоны: рейка модулей (64) → боковая панель модуля (200–380) → центр → **необязательная правая панель** (300–640). Правила:

* Правая панель открывается по выбору строки/карточки и **закрывается Esc**; её ширина запоминается на модуль.
* В ней — «карточка в миниатюре»: заголовок, 3–5 ключевых полей, главное действие, «Открыть полностью». Полная карточка — в центре. Это снимает дублирование между `Inspector` (лиды) и `CrmCard` (CRM).
* При центре < 560 px панель — плавающая поверх (уже реализовано), а не сжимающая таблицу.
* Левая панель показывает только то, что относится к выбранному модулю; рабочее пространство и аккаунт — в её шапке (§6.3).
* Не добавлять четвёртую колонку: на 880 px помещаются максимум три.

### 10.13. Принцип внедрения

Совместимый слой: новые токены вводятся как алиасы к старым; экраны переходят по одному; каждое изменение — отдельный пакет с макетом, тестом и скриншотом до/после (§12).
