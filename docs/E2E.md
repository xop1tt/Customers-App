# Приёмочные проверки на macOS и Windows (E2E)

Workflow `.github/workflows/e2e.yml` собирает настоящее приложение (Tauri 2) на macOS и Windows и прогоняет по нему
сценарии: нажимает кнопки, вызывает команды ядра, сверяет результат с эталоном (`desktop/e2e/golden`). Если сценарий
не прошёл — исправляется код приложения, а не проверка (CLAUDE.md §5).

## 1. Как это устроено и почему так

| Вопрос | Решение |
|---|---|
| Чем управлять окном | У WKWebView (macOS) нет WebDriver, поэтому Selenium/tauri-driver там не работают. Сценарий **вставляется в окно** самим приложением (флаг компиляции `--cfg e2e`, `Builder::on_page_load` + `webview.eval`) и выполняется внутри страницы: одинаково в WKWebView и WebView2. |
| Что собирается | Тот же путь, что у релиза: `tauri build` с `RUSTFLAGS="--cfg e2e"` (встроенный интерфейс, `custom-protocol`). Именно флаг компиляции, а не признак Cargo: раздел `[features]` в `Cargo.toml` запрещён тестом `test_release_check.py` (ADR-034). Флага нет в релизе: `release-check.cjs` проверяет, что `release.yml`/`desktop.yml` не упоминают e2e и `--cfg`, а `.cargo/config.toml` не создан. |
| Как отчёт попадает наружу | События Tauri `e2e-report`, `e2e-log`, `e2e-shot`; ядро пишет отчёт и журнал в папку прогона и завершает процесс с кодом 0 (всё прошло) или 1. Сторож завершает зависшее приложение кодом 3. |
| Внешние сервисы | Не используются: `RewriteTransport` подменяет адреса (лента RSS, GitHub, вебхук, WebDAV, Битрикс24, модель Ai) на локальный тестовый сервер `e2e/mock-server.cjs`. Сеть только в ночном/ручном прогоне (`live`). |
| Данные | Отдельная папка (`CUSTOMERS_E2E_DIR`), пароль собирается во время выполнения. Второй запуск приложения на тех же данных (`relaunch-*`) доказывает, что ключ базы переживает перезапуск в Связке ключей macOS и DPAPI Windows. |
| «Золотая» сверка | JSON-эталоны (`golden/*.json`), CSV (`*.golden.txt`), структура xlsx и список запросов, пришедших на тестовый сервер (`golden/received.json`). |
| Когда идёт | Каждый PR, затрагивающий `desktop/**`; push в `main`; ночью 03:23 UTC и вручную с галочкой `live` (настоящие GitHub и ленты). Обязательной можно сделать проверку **E2E gate** (успех или «пропущено» у всех задач). |

## 2. Матрица «функция → проверка»

| Функция | Сценарии | Что проверяется |
|---|---|---|
| Запуск и данные | `boot`, `paths`, `relaunch-boot` | окно не пустое, ядро отвечает, версия и платформа; запись только в отведённую папку; перезапуск |
| Аккаунт | `register`, `welcome`, `relogin`, `change-password`, `relaunch-login` | шифрованная база, ключ в системном хранилище, мастер первого запуска, смена пароля, старый пароль отклоняется |
| Навигация | `rail`, `navigation`, `quick-search` | все модули и разделы открываются без ошибок, быстрый поиск Ctrl/⌘+K |
| CRM: клиенты, контакты, сделки, задачи, заметки, звонки | `crm-core`, `crm-validation`, `crm-ui`, `relaunch-data`, `relaunch-ui` | создание и чтение, поиск, дубликаты, пустые и слишком длинные значения, показ на страницах «Сегодня», «Сделки», «Все клиенты», «Календарь», «Отчёты», «Журнал» |
| Корзина и массовые действия | `crm-trash`, `crm-bulk` | удаление и восстановление, выбор строк, «В корзину» с подтверждением |
| Импорт и экспорт | `import`, `import-undo`, `import-ui`, `export` | сопоставление колонок, дубликаты, отмена импорта; CSV и Excel сверяются с эталоном |
| Поиск клиентов | `search-settings`, `search-run`, `search-repeat`, `leads-ui`, `leads-exclude`, `lead-to-crm`, `live-search` | источники, фильтр слов, ETag/304 и память источника, избранное, архив, заметки, исключения, перевод лида в CRM |
| Настройки | `settings-sections`, `settings-theme`, `settings-language` | все разделы, светлая тема, английский и возврат на русский |
| Интеграции | `integrations-webhook`, `integrations-bitrix`, `integrations-webdav`, `integrations-mail-calls`, `integrations-ui` | вебхук, Битрикс24, WebDAV (проверка по полученным запросам), пресеты почты, хранение пароля |
| Ai | `ai-model`, `ai-ui` | список моделей, ответ, отказ по ключу, неверный адрес, сохранение настроек, выдвижной чат и настройки |
| Копии | `backup`, `portable` | резервная копия и восстановление, переносимая копия, неверный ключ отклоняется |
| Обновления | `updates-uptodate`, `updates-available`, `updates-checksum`, `updates-error`, `live-updates` | актуальная версия, найденная версия 99.0.0, чужая контрольная сумма, ошибка сервера, настоящий GitHub (ночью) |

Чего здесь нет и почему:

* Чат и команда работают через облако Supabase: приложение без облака проверяется на то, что страницы открываются без
  ошибок (`navigation`); сама синхронизация и права проверяются в `supabase/tests` (`Cloud gate`).
* Объединение дубликатов, права и миграции — модульные тесты ядра (`cargo test`) и интерфейса (`npm test`).
* Установка обновления (`updates-checksum`) выполняется только в установленной копии; в остальных случаях сценарий
  честно помечается как пропущенный, а не пройденный.

## 3. Запуск и обновление эталонов

Локально (из `desktop/`, нужны `npm run build` и Linux с `xvfb` либо macOS/Windows):

```
RUSTFLAGS="--cfg e2e" npx tauri build --no-bundle      # в PowerShell: $env:RUSTFLAGS="--cfg e2e"
node e2e/run.cjs --bin src-tauri/target/release/customers [--dir <папка>] [--live]    # или: npm run e2e -- --bin …
```

Для быстрой отладки на Linux: `RUSTFLAGS="--cfg e2e" cargo build --features tauri/custom-protocol --locked` в `src-tauri`, затем
`--bin src-tauri/target/debug/customers`. Итог: `summary.txt`, `report-*.json`, журнал и снимки экрана в папке
прогона; в CI они лежат в артефакте `e2e-<ОС>` 14 дней. Коды выхода `run.cjs`: 0 — всё прошло, 1 — есть
непройденные, 2 — прогон сломан (приложение не запустилось, отчёта нет).

Эталон меняется только осознанно, когда формат выгрузки изменили намеренно: `node e2e/run.cjs … --update-golden`, затем
посмотреть `git diff desktop/e2e/golden` и объяснить правку в PR.

## 4. Как добавить сценарий

Файл `desktop/e2e/scenarios/NN-имя.js` (порядок — по имени файла), внутри `E2E.scenario(id, описание, async () => {...}, опции)`.
Опции: `fatal` (остановить прогон при провале), `phase: "relaunch"`, `live` (только ночью), `mockOnly` (не в `live`).
Идентификатор нового сценария обязательно вносится в таблицу выше: `tests/test_e2e.py` это проверяет.
