# Резервные копии (пакет A1)

Две независимые копии, обе бесплатные (ADR-043):

| Что | Где | Как часто | Чем открыть |
|---|---|---|---|
| Локальная копия учётной записи: база лидов `leadgen-<время>.db` и рядом папка `leadgen-<время>.crm/` с базами всех Workspace и `catalog.json` | «Документы → Customers Backups → <учётная запись>» (или папка из настроек) | раз в сутки, перед удалением аккаунта, перед переносом, вручную | само приложение: «Настройки → Данные → Восстановить» |
| Снимок облака: схемы `public`, `private`, `auth` (данные CRM, лиды, участники, права, учётные записи) | GitHub → Actions → **Cloud backup** → артефакт `customers-db-<дата>` (90 дней) | каждый день, 02:23 UTC | `gpg` + `pg_restore` (ниже) |

## 1. Локальная копия

* Копия зашифрована тем же ключом учётной записи, что и рабочие базы (Связка ключей / DPAPI). Незашифрованная
  копия удаляется с ошибкой. Если базы CRM скопировать не удалось, не сохраняется и копия лидов: копия либо
  полная, либо её нет.
* Старые копии удаляются вместе с их папками `.crm` (настройка «Хранить копий»).
* Восстановление: база лидов как раньше; базы **локальных** Workspace (только на этом устройстве) заменяются
  копией, текущая база каждого сохраняется рядом как `<id>.before-restore.db`. Облачные Workspace не
  восстанавливаются из локальной копии: источник истины для них — сервер, они загружаются заново.
* Копии до пакета A1 (без папки `.crm`) восстанавливаются как раньше и CRM не трогают.
* Выгрузка копии на облачный диск («Выгрузить копию») пока отправляет только базу лидов.

## 2. Снимок облака (workflow `cloud-backup.yml`)

1. `supabase/cloud-backup/backup.py dump` открывает транзакцию, экспортирует снимок (`pg_export_snapshot`), считает
   строки каждой таблицы и запускает `pg_dump --snapshot` — счёт и снимок видят одно и то же состояние.
2. `backup.py check` восстанавливает снимок в пустой PostgreSQL 17 в раннере и сверяет число строк каждой
   таблицы. Не совпало — workflow красный, артефакт не сохраняется. Так проверка восстановления идёт каждый
   день, а не раз в месяц.
3. Снимок и `manifest.json` упаковываются в `tar` и шифруются `gpg --symmetric --cipher-algo AES256` паролем
   `BACKUP_PASSPHRASE`. В артефактах лежит только зашифрованный файл.

Workflow только читает базу. На стенде CI (`cloud.yml`) тот же скрипт проверяется тестом
`supabase/tests/test_backup.py`.

### Настройка (один раз, делает Maksim)

1. Supabase → проект **Customers** → кнопка **Connect** → **Session pooler** → скопировать URI
   (`postgresql://postgres.ldbbbssoevprnrbhcnjy:[YOUR-PASSWORD]@aws-…pooler.supabase.com:5432/postgres`) и
   подставить пароль базы. Прямое подключение (`db.….supabase.co`) не подходит: у раннеров GitHub нет IPv6.
2. Придумать длинный пароль шифрования (например, 6–8 случайных слов) и **сохранить его в менеджере паролей**.
   Без него копии не расшифровать.
3. GitHub → репозиторий → **Settings → Secrets and variables → Actions → New repository secret**:
   `SUPABASE_DB_URL` = строка из п. 1, `BACKUP_PASSPHRASE` = пароль из п. 2.
4. **Actions → Cloud backup → Run workflow** и убедиться, что запуск зелёный и появился артефакт.

Пока секреты не заданы, workflow падает с понятной ошибкой: отсутствие копии не должно быть тихим.

### Восстановление

```bash
gpg --decrypt customers-db-2026-11-11.tar.gpg > backup.tar && tar -xf backup.tar
pg_restore --list customers.dump | less          # что внутри
# Восстановление в новый проект Supabase (сначала применить supabase/migrations или восстановить целиком):
pg_restore --no-owner --no-acl --data-only -d "СТРОКА_ПОДКЛЮЧЕНИЯ_НОВОГО_ПРОЕКТА" customers.dump
```

Восстановление в **рабочий** проект — необратимая операция: только по отдельному решению Maksim, после
проверки на копии.
