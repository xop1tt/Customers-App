# Журнал архитектурных решений (Customers 2.0)

Каждое решение имеет номер, дату, статус и причину. Последующие этапы не должны противоречить принятым
решениям; если решение нужно изменить, добавляется новая запись «заменяет ADR-NNN», старая не удаляется.

Статусы: **принято** (действует), **реализовано** (есть в коде и проверено тестами), **заменено**.

| № | Дата | Решение | Статус |
|---|---|---|---|
| 001 | 2026-11-09 | Сохраняем стек: Tauri 2 + React + TypeScript + Rust, SQLite/SQLCipher локально, Supabase (Auth, Postgres, Realtime, Storage) в облаке. Без отдельного backend-сервера; серверная логика — SQL-функции и Edge Functions. | принято |
| 002 | 2026-11-09 | Workspace-first: все CRM-данные принадлежат `workspace_id`. Права проверяет PostgreSQL (RLS + функции), интерфейс только скрывает недоступное. | принято |
| 003 | 2026-11-09 | Генератор лидов остаётся отдельным модулем со своими таблицами (`public.leads`, `exclusions`, `user_settings` — пользовательские, как сейчас). CRM не нужна для поиска, поиск не нужен для CRM. Связь — только операция «Преобразовать в CRM». | принято |
| 004 | 2026-11-09 | Таблица найденных лидов `public.leads` не переименовывается и не меняется: на неё опираются установленные версии. CRM-запись «лид/клиент» — новая таблица `public.crm_leads`. | принято |
| 005 | 2026-11-09 | Права — по разрешениям (`permissions`, `role_permissions`), а не по названиям ролей. Пять системных ролей — шаблоны с `workspace_id IS NULL`; свои роли Workspace — строки с его `workspace_id`. | принято |
| 006 | 2026-11-09 | Синхронизация CRM — то же устройство, что уже работает для лидов: `server_seq` + курсоры, время изменения каждого поля (`field_ts`), надгробия. Добавляется: идентификатор операции `op_id` (идемпотентность), `version` строки и журнал конфликтов для одновременной правки одного поля. Связи «многие ко многим» — строки-связи со своими надгробиями (без LWW над массивами). | принято |
| 007 | 2026-11-09 | Realtime используется только как «звонок» (`{table, server_seq}` по приватному каналу Workspace), данные приходят обычным запросом с курсором. Нет постоянного опроса сервера. | принято |
| 008 | 2026-11-09 | Локально у каждого Workspace свой зашифрованный файл SQLite (`<папка учётной записи>/workspaces/<id>.db`) и своя очередь операций. Выход из Workspace удаляет только этот файл (после отчёта о неотправленных изменениях). | принято |
| 009 | 2026-11-09 | Существующие облачные пользователи получают личный Workspace при первом входе новой версии через идемпотентную RPC `ensure_personal_workspace()`, а не массовой миграцией рабочей базы. Локальные учётные записи получают локальный Workspace. | принято |
| 010 | 2026-11-09 | Миграции только добавляют: старые файлы `supabase/migrations/*` не меняются, локальная схема растёт шагами `schema_version` с копией базы перед шагом и сверкой числа строк после. | принято |
| 011 | 2026-11-09 | Два канала приложения — Stable и Beta — выбираются при сборке (признак Cargo `beta` + `tauri.beta.conf.json`). У Stable все идентификаторы прежние; у Beta свои идентификатор, имя, исполняемый файл, папки, секреты, схема ссылок, установщик, облако. Любая отладочная сборка (`debug_assertions`) — Beta. | реализовано (этап 1) |
| 012 | 2026-11-09 | Защита от пересечения каналов проверяется при запуске до записи любых файлов (идентификатор, папки, метка канала) и при каждом пути, выбранном пользователем (перенос базы, восстановление, экспорт, папка копий). Beta не открывает незашифрованные базы (их могла создать только Stable 1.0). | реализовано (этап 1) |
| 013 | 2026-11-09 | Beta не проверяет и не ставит обычные релизы (иначе изменила бы Stable); Stable не видит Pre-release и файлы `Customers-Beta-*`. Обновление Beta — вручную со страницы Pre-release; встроенное обновление Beta — этап 2. | реализовано (этап 1) |
| 014 | 2026-11-09 | Облако Beta — отдельный проект Supabase (переменные `SUPABASE_BETA_URL`, `SUPABASE_BETA_ANON_KEY`). Без них Beta собирается без облака. Совпадение с рабочим проектом останавливает сборку. | реализовано (этап 1) |
| 015 | 2026-11-09 | Ветки: `main` — Stable, `develop` — следующая версия, `feature/*` — крупные задачи. Версии: SemVer, Beta — `X.Y.Z-beta.N`. Источник версии — тег; `set-version.cjs` пишет её в три файла, `release-check.cjs` проверяет согласованность. | реализовано (этап 1) |
| 016 | 2026-11-09 | Публикация Stable — только `release.yml`, задача `publish` в окружении `production` (обязательный ревьюер задаётся в настройках GitHub). Beta — `beta.yml`, только `--prerelease`, только по тегу `v*-beta.*`. | реализовано (этап 1) |
| 017 | 2026-11-09 | Debug Menu, Scenario Runner, генераторы тестовых данных — модуль `src-tauri/src/debug`, подключаемый только `#[cfg(feature = "beta")]`; `release-check.cjs` не пропустит иное. | реализовано (этап 2) |
| 018 | 2026-11-09 | Пользовательские поля — типизированная таблица значений (`value_text`, `value_number`, `value_date`, `value_ts`, `value_bool`, `value_json`) с частичными индексами по типу, а не JSON в строке сущности: фильтры и сортировка по индексу, синхронизация построчно. | принято |
| 019 | 2026-11-09 | Коллекция — сохранённое представление (фильтры, сортировка, колонки) над существующими таблицами; данных не копирует. Личная (`visibility = private`) или общая для Workspace. | принято |
| 020 | 2026-11-09 | Интерфейс: сохраняем компоновку и Flat Dark. Добавляются ровно три элемента: аватары сотрудников справа в верхней панели, крупная иконка раздела у заголовка, секция «Коллекции» в левой панели (см. CRM_ARCHITECTURE.md §8). | принято |
| 021 | 2026-11-09 | Команды Debug Menu — отдельный `generate_handler!` (`debug_handler`) только при `beta`; общий обработчик передаёт ему вызовы с префиксом `debug_`. Список команд Stable не меняется. | реализовано (этап 2) |
| 022 | 2026-11-09 | Зависимости Debug Menu — только `optional = true` и включаются признаком `beta` (`dep:…`); сейчас это одна `sysinfo`. Отчёт ZIP пишется своим кодом без сжатия (≈100 строк, CRC-32), чтобы не добавлять библиотеку архивов. | реализовано (этап 2) |
| 023 | 2026-11-09 | Тестовые данные — только в локальной учётной записи Beta с отметкой «тестовая», никогда при облаке или синхронизации; генератор детерминированный по `seed`; сброс — со словом «сброс». | реализовано (этап 2) |
| 024 | 2026-11-09 | Сценарии Scenario Runner — функции над настоящим `Core` во временной папке со своим `Env` (секреты в памяти, без сети и облака); один и тот же код запускается из Debug Menu и `cargo test --features beta --test scenarios`. Сценарии, которым нужны сеть или облако, добавляются только вместе со стендом, который их реально проверяет, — без заглушек. | реализовано (этап 2) |
| 025 | 2026-11-10 | CRM-ядро клиента — модуль `workspace/` (имя `crm/` уже занято выгрузкой в Bitrix24/Notion), команды `ws_*`. Одна база SQLCipher на Workspace: `workspaces/<id>.db`; список и активный — `workspaces/catalog.json`. | реализовано (этап 3) |
| 026 | 2026-11-10 | Права проверяет сервер: `private.has_perm` (security definer, `search_path=''`), RLS на каждой таблице, запись в таблицы прав — только через RPC. Клиент повторяет проверку только чтобы не ставить в очередь заведомо отклоняемое. | реализовано (этап 3) |
