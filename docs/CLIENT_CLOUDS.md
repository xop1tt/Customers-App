# Облака клиентов: где хранится база Workspace

ADR-098. Решение Maksim (2026-11-22): клиент сам выбирает, где размещать базу облачного Workspace, и в любом варианте
ему сразу предлагается улучшение до платного тарифа у выбранного сервиса. Платит клиент сервису напрямую; у
владельца Customers трат нет.

| Вариант | Где база | Кто платит | Улучшение |
|---|---|---|---|
| Общее облако Customers | проект Supabase Customers | никто (бесплатно, жёсткий лимит 300 МБ вложений на Workspace) | — |
| Свой Supabase | проект в аккаунте Supabase клиента | клиент, Supabase | «Улучшить до Pro» (страница оплаты Supabase) |
| Свой сервер | сервер у хостинга клиента с Supabase | клиент, хостинг | «Сервер побольше» |

Хостинги для «Своего сервера»: Hetzner, DigitalOcean, Vultr, Akamai (Linode), Timeweb Cloud, Selectel.

## Пакеты

1. **Основа (этот документ, сделано).** У каждого облачного Workspace своё облако и свой вход.
2. Мастер: выбор варианта при создании Workspace.
3. Свой Supabase: вход в аккаунт Supabase (OAuth), создание бесплатного проекта, установка схемы, «Улучшить до Pro».
4. Свой сервер: ключ API хостинга, аренда сервера, установка Supabase, «Сервер побольше».
5. Обновление схемы в облаках клиентов при выходе новой версии.

## Как устроена основа

* Учётная запись приложения и всё «личное» (лиды, настройки, личный Workspace, каталог интеграций) остаются в
  общем облаке Customers.
* `WorkspaceInfo.cloud` (`workspace/catalog.rs`): `None` — общее облако, `Some(CloudRef { url, anon_key, kind })` —
  облако клиента. Адрес и ключ публичные (как встроенные в приложение), секретный ключ не принимается
  (`CloudConfig::is_public_key`).
* `Catalog.clouds` — подключённые облака клиента, даже без Workspace. Список Workspace общего облака и каждого облака
  клиента обновляется отдельно (`replace_remote` / `replace_cloud`): недоступное облако не стирает чужие Workspace.
  В облаке клиента нет личного Workspace (`client_workspaces` не вызывает `ensure_personal_workspace`).
* У облака клиента **свой вход и свой id пользователя**: Supabase не принимает вход из чужого проекта. Сессия хранится
  в защищённом хранилище под именем `cloud.client.<sha256(учётная запись + адрес)>` (`ClientSessionStore`), так что
  другая учётная запись на этом компьютере не получит чужой вход. `Env::client_cloud` открывает клиента облака по
  требованию.
* Все запросы Workspace (синхронизация CRM, участники, приглашения, роли, отделы, журнал, вложения, присутствие,
  чат, Realtime) идут в облако **выбранного** Workspace (`Core::cloud_of` / `active_cloud`); «я» в Workspace — id
  пользователя этого облака (`me_in`).
* Каталог интеграций живёт в общем облаке: для Workspace в облаке клиента установка интеграций пока недоступна
  (код ошибки `clientCloud`).
* Отключение облака (`ws_cloud_disconnect`) только забывает вход на устройстве и удаляет локальные копии его
  Workspace (неотправленные изменения сохраняются в файл, как при удалении из Workspace). В самом облаке ничего не
  удаляется.

## Команды ядра

| Команда | Что делает |
|---|---|
| `ws_clouds` | подключённые облака: адрес, вид, вошли ли, сколько Workspace |
| `ws_cloud_connect(url, anonKey, kind, email, password, signUp)` | подключить и войти (или зарегистрироваться → `confirm`) |
| `ws_cloud_verify(url, email, code)` | код из письма после регистрации |
| `ws_cloud_disconnect(url)` | отключить на этом устройстве |
| `ws_create_workspace(name, cloud?)` | создать Workspace в общем облаке или в облаке клиента |
| `ws_upload_local(cloud?)` | перенести локальный Workspace в общее облако или в облако клиента |

## Что требуется от облака клиента

Та же схема, что у общего облака (`supabase/migrations`), той же или более новой версии. Устанавливать её будет мастер
(пакеты 3 и 4); до этого облако клиента настраивается вручную по `docs/cloud-setup.md`.
