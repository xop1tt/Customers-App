# План миграций и сохранения данных

Главный критерий: ни одна запись пользователя не теряется, установленная Stable-версия продолжает работать.

## 1. Проверенное состояние (2026-11-09)

* Локальная база генератора — `schema_version 2` (`store.rs`); старые незашифрованные базы переписываются в
  зашифрованные с проверкой `quick_check` и числа строк до удаления исходника (`db::migrate_plaintext`), прерванная
  замена доводится или откатывается при следующем запуске.
* Supabase — две миграции (схема синхронизации лидов, лимиты писем), применены на рабочем проекте 2026-11-06.
* Модели CRM в обеих базах пока нет — переходить нечему, кроме учётных записей и лидов.
* 2026-11-10: добавлены миграции этапов 3–7 (`20261110120000_workspaces.sql` … `20261110120400_collections.sql`),
  только новые объекты; проверены на стенде (с нуля и повторно, `test_migrations.py`). На рабочий проект и проект
  Beta **не применялись** — нужно отдельное разрешение Maksim.

## 2. Совместимость моделей

| Сейчас | В 2.0 | Перенос |
|---|---|---|
| Облачная учётная запись (`auth.users`) | пользователь + `user_profiles` + личный Workspace | `ensure_personal_workspace()` при первом входе 2.0; имя профиля — из `profile.name` (`user_settings`) |
| Лиды, исключения, настройки (`public.leads` и др., по `user_id`) | без изменений (модуль генератора) | не нужен |
| Локальная учётная запись (без облака) | локальный Workspace на устройстве | создаётся локально; при подключении облака выгружается как личный Workspace (операции очереди) |
| Лид генератора | может породить компанию/контакт CRM | по команде пользователя (`convert_lead`), лид остаётся |

## 3. Порядок

1. **Этап 1 (сделано)** — каналы. Никаких миграций Stable: Stable-сборка из этой ветки использует те же папки,
   идентификаторы, ключи и схему, что установленная версия (тесты `stable_identity_matches_previous_versions`,
   `standard_folders_match_previous_versions`, `release-check`).
2. **Этап 3, сервер** — новые файлы миграций (DATABASE_SCHEMA.md §3), только `create … if not exists`.
   Проверка: стенд CI применяет все миграции с нуля и повторно (идемпотентность), затем тесты старого протокола
   (`test_sync_rls.py`) — старые версии приложения работают на новой схеме.
   Применение на рабочем проекте — **только с отдельного разрешения Maksim**, сначала на проекте Beta.
3. **Этап 3, клиент** — база Workspace создаётся новым файлом; база генератора не меняется.
4. **Перенос пользователя** — при первом входе 2.0: `ensure_personal_workspace()` (идемпотентно), затем загрузка.
   Без сети: приложение работает с локальным Workspace и создаёт личный, когда сеть появится.
   *Реализация:* облачная учётная запись открывает CRM после первого успешного `ensure_personal_workspace`;
   до этого генератор лидов работает как прежде. Выгрузка CRM-данных локальной учётной записи в облако при
   подключении облака — **запланировано** (сейчас переносятся только лиды, как в 1.x).

## 4. Правила любой будущей миграции локальной базы

* Перед шагом — копия файла рядом (`<имя>.pre-v<N>.db`, через `sqlite3_backup`, зашифрованная тем же ключом).
* Шаг — в одной транзакции; `schema_version` меняется в ней же.
* После шага — `PRAGMA quick_check` и сверка числа строк таблиц, которые шаг не должен менять (`db::row_counts`);
  при расхождении — откат и возврат копии, приложение открывается в прежней схеме и показывает ошибку.
* Частично выполненный шаг (сбой посреди) — транзакция не зафиксирована, при запуске шаг повторяется.
* Копии старше двух успешных запусков удаляются.

## 5. Правила миграций сервера

* Старые файлы не меняются никогда; исправление — новая миграция.
* Каждая миграция повторяема, проверяется на стенде с нуля и поверх предыдущих.
* Скрипт проверки после применения (`supabase/tests/test_migrations.py`, этап 3): число строк `leads`,
  `exclusions`, `user_settings` до и после равно; все таблицы `public` имеют RLS (`relrowsecurity` и
  `relforcerowsecurity`); у каждой definer-функции задан `search_path`; у `anon` нет прав на таблицы.
* Необратимые операции (удаление столбцов/таблиц, массовые изменения данных) — отдельная миграция только после
  подтверждения Maksim и резервной копии проекта: на тарифе Free нельзя рассчитывать на восстановление из
  управляемых копий, поэтому перед такой миграцией обязательна выгрузка `supabase db dump` (схема и данные `public`).
