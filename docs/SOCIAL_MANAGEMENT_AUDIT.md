## 0. Как читать

Обозначения для Customers: **есть** — работает в приложении; **только база** — RPC/таблица/право есть, экрана или команды клиента нет;
**нет** — не найдено в коде. Для конкурентов: **✔** — прочитано мной на официальной странице вендора в этой сессии (источник в §9);
**◇** — страница найдена поиском, но её текст не читался (по названию, без деталей); **?** — не проверено, не утверждаю.
Тарифные ограничения приведены, только если страница их называет.

Что проверено в Customers: миграции `20261110120000_workspaces`, `…120100_crm_core`, `…130200_presence`, `…170000_team_chat`,
`…20261111090000_chat_live_attachments`; экраны `desktop/src/app/team/*`, `crm/WorkspaceDialog.tsx`, `crm/Presence.tsx`, `CrmCard.tsx`,
`lib/crm.ts`, `lib/team.ts`; список команд `ws_*` в `commands.rs`. Приложение не запускалось, UX оценён по коду и по тексту интерфейса

### Рекомендуемый порядок

1. **A1 + A2** (S-03, S-04, P0) — самое больное при первом же уходе сотрудника.
2. **A4, A3, A5** — приглашения, журнал, владение: всё уже готово в базе, не хватает экранов.
3. **A6, A7, A8, A9** — удобство.
4. **B1 → B2 → B3** одним PR с базой: назначения, отделы, доступ по иерархии. B3 не брать без отдельного решения о модели доступа.
5. **A10/A11** — только если B откладывается надолго.

Не предлагаю (противоречит курсу): SSO/SCIM и корпоративные каталоги, публичный API управления пользователями, мобильные уведомления,
платные тарифные ограничения «по местам».

## 6. Решения Maksim (2026-11-12) и ход работ

* Пакет **A1+A2** — «да», выполнен: диалог «Передать записи» (список участников и профиль), передача при удалении участника,
  подпись «Бывший участник» (ADR-074). Завершённые записи (выигранные/проигранные сделки, выполненные задачи, закрытые заявки)
  остаются за прежним ответственным.
* Пакеты **A3 (журнал действий) и A4 (приглашения: список, повтор, отзыв)** выполнены по «давай» (ADR-075). Пакет **A5** (передача владения, удаление Workspace) выполнен после согласования текстов (ADR-076). Затем выполнены A6–A9 и справочник отделов (ADR-077). Остаются A10–A11.
* **Видимость данных по иерархии нужна** (B3). Это права и RLS, поэтому по правилам этапа 3 откладывается в этап базы; ждёт
  решения о новой базе. До тех пор — фильтры A7.
* **Отдел** — справочник поверх текста («Сотрудники» → «Отделы», ADR-077); настоящая сущность «отдел» (B2) — в этап базы с нуля.
* **A5** (передача владения, удаление Workspace) — подтверждено; делается отдельным пакетом после A1+A2.

Вопросы, заданные в первой редакции документа (для истории):

1. Пакет **A1+A2** (передача записей и метка бывшего сотрудника) — делать первым? (рекомендую да)
2. Нужна ли **иерархическая видимость** (B3) или достаточно «все видят всё» + фильтры A7? Для команды до ~10 человек достаточно второго.
3. **Отдел** остаётся текстом (A7) или станет сущностью (B2, потребует базу)?
4. **Передача владения и удаление Workspace** (A5) — необратимые действия: подтверждаете формулировки на макетах (CLAUDE.md §7)?

## 7. Что не удалось проверить

* Интерфейс на устройстве, реальный чат и присутствие (по коду; облачный стенд не поднимался).
* Конкуренты: Chatter (Salesforce), мессенджер Bitrix24, командный чат Dynamics/Teams, Zoho Cliq, Freshsales «mentions», HubSpot
  «notifications» — страницы найдены, **тексты не читались**, поэтому отмечены ◇ или «?».
* Salesforce: страница «Sharing and Record Access Features» отдаёт только оболочку (JS), слои модели общего доступа не подтверждены
  (роли и менеджерские группы подтверждены).
* Тарифные ограничения Zoho (число групп/ролей по редакциям) и HubSpot (число команд) страницы не называют.
* «Влияние на БД» оценено по схеме миграций из репозитория; в рабочем Supabase миграции 20261111120000 и 20261111130000 не применены
  (память проекта), поэтому часть Realtime/вложений чата может отсутствовать на сервере — **не проверялось** (запись и подключение к
  Supabase не выполнялись).
