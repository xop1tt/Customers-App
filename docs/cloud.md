# Облако Lead Generator: учётные записи, лимиты писем, синхронизация

Технический документ. Пошаговая настройка для неспециалиста — в [cloud-setup.md](cloud-setup.md).

Всё работает на бесплатном тарифе Supabase (Free) и бесплатном SMTP (например, Gmail с паролем
приложения). Платные сервисы, домены и подписки не нужны. Облако — **отдельный проект Supabase**
только для Lead Generator; другие ваши проекты (в том числе «Mirada») не используются и не меняются.

## 1. Что из чего состоит

```
Приложение (macOS и Windows) ──HTTPS──► Supabase (проект Lead Generator)
  desktop/src-tauri/src/cloud (Rust) ├─ Auth (GoTrue): почта + пароль, токены
  ├─ CloudAuth: вход, токены        │    └─ Send Email Hook ──► функция send-email ──SMTPS──► почта
  ├─ SyncEngine: выгрузка/загрузка  ├─ функция email-gate: лимиты писем, разовый «билет»
  └─ журнал sync_dirty в SQLite     ├─ функция delete-account: удаление учётной записи
                                    └─ Postgres: leads, exclusions, user_settings (RLS)
```

| Часть | Где | Что делает |
|---|---|---|
| `supabase/migrations/20261106120000_sync_schema.sql` | Postgres | таблицы данных, RLS, `sync_push`, `sync_stats` |
| `supabase/migrations/20261106120100_email_limits.sql` | Postgres, схема `private` | лимиты писем, учёт отправок |
| `supabase/functions/email-gate` | Edge Function | проверяет лимиты до запроса письма, выдаёт билет |
| `supabase/functions/send-email` | Edge Function (хук Auth) | требует билет, резервирует квоту, отправляет письмо |
| `supabase/functions/delete-account` | Edge Function | удаляет учётную запись после повторного ввода пароля |
| `desktop/src-tauri/src/cloud` | приложение | клиент Auth (`auth.rs`) и синхронизации (`sync.rs`), проверка данных (`validation.rs`) |
| `desktop/src-tauri/src/db.rs` | приложение | журнал изменений, применение данных с сервера |
| `desktop/src-tauri/src/app/session.rs`, `app/sync.rs` | приложение | хранилище секретов, фоновая синхронизация, вход |

В приложении хранятся только **адрес проекта и публичный ключ** (anon / publishable). Они попадают в
приложение при сборке из переменных окружения `SUPABASE_URL` и `SUPABASE_ANON_KEY`. Приложение отказывается
работать с секретным ключом (`sb_secret_…` или JWT с ролью не `anon`). Ключ `service_role` есть только
у функций на сервере (Supabase передаёт его им сам).

## 2. Учётные записи

- Регистрация по почте и паролю. Пароль: не короче 8 символов, строчные и заглавные буквы и цифры
  (проверяется в приложении и в Auth).
- Подтверждение почты: письмо с 6-значным кодом и ссылкой. Ссылка ведёт на `…/auth/v1/verify` и
  возвращает в приложение по `leadgenerator://auth/callback`. Код работает всегда, даже если почтовый
  клиент не открывает такие ссылки.
- Вход по паролю писем не тратит. Повторные неверные пароли Auth ограничивает по IP (на стенде:
  30 попыток за 5 минут, дальше `429`). Сообщение об ошибке одинаковое для неверного пароля и
  несуществующего адреса.
- Сессия: access-токен (1 час) и одноразовый refresh-токен в хранилище секретов (Связка ключей macOS, DPAPI на Windows). Токен обновляется
  заранее; параллельные запросы ждут одно обновление. Повторное использование старого refresh-токена
  отзывает всю цепочку (защита от кражи). Без сети приложение открывается с локальными данными.
- Восстановление пароля: код из письма → новый пароль. После смены пароля другие сессии завершаются.
- Смена пароля: нужен текущий пароль; другие устройства выходят.
- Смена адреса (Secure email change): нужен пароль; письма уходят **на оба адреса**, адрес меняется
  только после подтверждения обоих. Стоит 2 письма из лимитов.
- Удаление: пароль вводится заново (функция проверяет, что вход по паролю был не более 10 минут
  назад), затем удаляются учётная запись и все её строки в облаке (`on delete cascade`). Перед этим
  приложение сохраняет копию базы в папку резервных копий; без копии удаление не начинается.
- Локальные учётные записи (имя + пароль, только на этом Mac) остались как были. Их данные можно
  перенести в облачную: «Настройки → Учётная запись → Перенести данные локальной учётной записи».
- Google/Apple: `CloudAuth` работает с сессией Auth независимо от способа входа, а
  `handleCallback` уже принимает токены из ссылки. Чтобы добавить OAuth, нужен вызов
  `/auth/v1/authorize?provider=…` с PKCE и кнопка на экране входа; схема данных и синхронизация не меняются.

## 3. Лимиты писем

### Как устроено

1. Приложение просит `email-gate` разрешить письмо (`action`, `email`, `device_id`).
   Функция проверяет лимиты в Postgres и выдаёт **разовый билет** на 10 минут.
2. Приложение вызывает Auth (`/signup`, `/resend`, `/recover`, `PUT /user`).
3. Auth вызывает хук `send-email`. Хук проверяет подпись (Standard Webhooks), находит билет,
   **атомарно** резервирует место в лимитах (общая advisory-блокировка `leadgen-email-quota`),
   отправляет письмо по SMTPS и отмечает результат.
4. Ошибка SMTP — резерв снимается, билет возвращается, квота не тратится. Повтор того же
   `webhook-id` не отправляет письмо второй раз.

### Значения по умолчанию (таблица `private.email_limits`, меняются одним `update`)

| Правило | Значение |
|---|---|
| Регистрация | 1 письмо сразу, повтор — не чаще 1 раза в 15 минут |
| Восстановление пароля | 1 раз в 30 минут |
| Смена адреса | 1 раз в 30 минут (2 письма: старый и новый адрес) |
| Один адрес | не больше 5 писем в сутки, все операции вместе |
| Одно устройство | 3 в час, 5 в сутки |
| Один IP | 10 в час, 30 в сутки (с запасом на NAT: офис, мобильная сеть) |
| Всё приложение | 50 писем в сутки |
| Сутки | по Москве (`day_timezone = 'Europe/Moscow'`) |

Изменить, например, общий лимит:

```sql
update private.email_limits set global_daily_max = 80;
select public.email_quota_status();   -- сколько отправлено сегодня
```

Общий суточный лимит считает только реально отправленные письма (`sent`) и письма в процессе
отправки (`reserved`); неудачные (`failed`) не учитываются. Интервалы и лимит одного адреса шлюз
считает по выданным разрешениям (талонам): Auth не отправляет писем несуществующим адресам, и счёт по
отправкам позволил бы через шлюз узнать, есть ли аккаунт. Талон, письмо по которому не ушло из-за
ошибки почты, не учитывается. Если из двух писем смены адреса ушло одно, оно учитывается как отправленное. Хранятся только SHA-256 от адресов, устройств и IP, журнал
очищается через 8 дней.

### Что гарантировано, а что нет

- **Общий суточный лимит гарантирован** для писем, которые отправляет Auth: хук считает квоту сам,
  даже если кто-то вызывает Auth API напрямую, минуя приложение. Это проверено тестом
  `test_global_limit_holds_without_gate_tickets` и тестом на 30 параллельных резервирований при лимите 5.
- Запрос напрямую в Auth без билета письма **не отправляет** и пользователя не создаёт
  (`require_gate_ticket = true`): Auth получает ошибку хука и откатывает регистрацию.
- Лимит **устройства** — мягкий: идентификатор устройства задаёт клиент, его можно подменить. Поэтому
  он дополняет, а не заменяет лимиты адреса, IP и общий.
- Лимит **IP** зависит от того, какой заголовок с адресом клиента приходит в функцию. По умолчанию
  берутся `cf-connecting-ip`, затем `x-real-ip`, затем последний `x-forwarded-for`; порядок меняется
  секретом `CLIENT_IP_HEADERS`. После развёртывания это стоит проверить (см. cloud-setup.md, шаг 9).
- Письма, которые Auth отправляет **не через хук** (например, приглашения из панели Supabase), этим
  механизмом не считаются. Уведомления Auth («пароль изменён» и т. п.) хук не отправляет вовсе.
- Если функция упала между резервированием и отметкой, строка остаётся `reserved` и занимает место до
  конца суток (в безопасную сторону).
- У почтового сервиса свой суточный лимит (Gmail — около 500, Brevo Free — 300). Он выше нашего, и
  ограничивает отправку именно хук.

## 4. Данные и синхронизация

### Что синхронизируется

| Данные | В облаке |
|---|---|
| Лиды: данные, избранное, архив, удаление, просмотр, заметка | `public.leads` |
| Исключения (домены, телефоны, слова…) | `public.exclusions` |
| Настройки поиска, интервал автопоиска, подпись | `public.user_settings` (`search.settings`, `search.auto`, `draft.signature`) |

Остаются на устройстве: оформление, ключ VK (хранилище секретов), пути к базе и копиям, память источников
(что уже прочитано), журнал поиска, история действий.

### Схема

- Ключ строки — `(user_id, lead_id)` / `(user_id, kind, value)` / `(user_id, key)`; `user_id` ссылается на
  `auth.users` с `on delete cascade`.
- RLS включён и принудителен (`force row level security`): `authenticated` видит и меняет только строки с
  `user_id = auth.uid()`; у `anon` прав нет. Проверено тестами `test_sync_rls.py`.
- `server_seq` — номер изменения из общей последовательности. Триггер берёт advisory-блокировку на
  пользователя, поэтому номера идут в порядке фиксации транзакций и загрузка «после N» ничего не пропускает.
- `field_ts` — время изменения каждого поля лида. Время клиента (и `discovered_at`) не может быть позже `now()` сервера: это обеспечивает триггер, даже при записи в таблицу в обход `sync_push`.
- Удаление — «надгробие»: `deleted = true`, строка остаётся, чтобы удаление дошло до всех устройств.

### Протокол (одинаковый для macOS и будущего Windows-клиента)

- **Выгрузка:** `POST /rest/v1/rpc/sync_push` с `{"p_device": "...", "p_changes": {"leads": [...],
  "exclusions": [...], "settings": [...]}}`, до 500 элементов. У лида передаются все поля и `ts` —
  время изменения тех полей, что менялись на устройстве. Сервер для каждого поля оставляет более позднее
  изменение (last-writer-wins по полю), для исключений и настроек — по `changed_at`.
- **Загрузка:** `GET /rest/v1/<таблица>?select=*&server_seq=gt.<курсор>&order=server_seq.asc&limit=500`
  для `leads`, `exclusions`, `user_settings`; у **каждой таблицы свой курсор** — наибольший полученный
  из неё `server_seq` (номера в одной таблице идут в порядке фиксации, поэтому ничего не пропускается).
- **Сводка:** `POST /rest/v1/rpc/sync_stats` — сколько строк в облаке (для проверки переноса).
- Заголовки: `apikey: <публичный ключ>`, `Authorization: Bearer <access-токен>`.

### На устройстве

- Каждое изменение пишется в журнал `sync_dirty` **в той же транзакции SQLite**, что и данные:
  аварийное завершение ничего не теряет, журнал уйдёт при следующей синхронизации.
- Синхронизация: выгрузка → загрузка → выгрузка. Запускается через 3 секунды после изменения,
  раз в минуту, при появлении сети и кнопкой «Синхронизировать сейчас». Одновременно — не больше одной.
- Конфликт: если поле изменено и здесь, и на другом устройстве, остаётся более позднее изменение;
  локальное изменение, которое новее пришедшего, не затирается и уйдёт на сервер.
- Изменения с сервера в журнал не попадают — нет эха «загрузил → выгрузил».
- Восстановление базы из резервной копии в облачной учётной записи отмечает всё для выгрузки и
  загружает облако заново.
- Перенос локальной учётной записи: данные копируются с временем изменения 2000-01-01, поэтому
  не затирают то, что уже есть в облаке. Лиды с тем же id или отпечатком не дублируются. Исходная база
  не меняется. Перед переносом сохраняется резервная копия.

## 5. Ограничения бесплатного тарифа Supabase

- 2 активных бесплатных проекта на организацию; база до 500 МБ; 50 000 активных пользователей в месяц;
  500 000 вызовов функций в месяц. Lead Generator в эти рамки укладывается с большим запасом.
- **Проект на паузе после 7 дней без запросов.** Приложение тогда работает локально и сообщит, что нет
  связи с сервером; проект возобновляется кнопкой в панели Supabase, данные сохраняются.
- Резервные копии базы на Free не входят: делайте выгрузку через `pg_dump` (cloud-setup.md, шаг 11);
  кроме того, у каждого пользователя полная копия данных на его Mac.
- Проверка паролей по базе утечек (Leaked password protection) и хук проверки пароля — только на
  платных тарифах; не используются.

## 6. Проверка на локальном стенде

Стенд поднимается без облака и без секретов (Linux, нужны PostgreSQL 16, Docker, Python 3.12, Deno 2):

```bash
supabase/tests/stack/up.sh                 # Postgres-база leadgen_test, Auth, PostgREST, функции, SMTP-заглушка
python -m pytest supabase/tests            # 52 теста: вход, лимиты, RLS, синхронизация
(cd supabase/functions && deno test --allow-env _shared/shared_test.ts)
(cd desktop/src-tauri && LG_STACK_URL=… LG_STACK_ANON=… LG_STACK_MAIL=… cargo test --test stack)   # Rust: сквозные тесты двух «устройств»
supabase/tests/stack/down.sh
```

В CI это делает workflow `.github/workflows/cloud.yml`. Сборка и запуск приложения проверяются в
`desktop.yml` на macOS и Windows.
