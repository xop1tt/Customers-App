## Сборка приложения

Нужны Xcode 15+ или Command Line Tools (`xcode-select --install`).

```bash
cd macos
swift test                                       # тесты
./scripts/build-app.sh                           # build/Customers.app
./scripts/make-dmg.sh build/Customers.dmg   # установщик
open "build/Customers.app"
```

Для разработки: `open Package.swift` откроет проект в Xcode, схема `LeadGenerator`.

Облако включается в сборке переменными `SUPABASE_URL` и `SUPABASE_ANON_KEY` (они попадают в `Info.plist`),
см. [docs/cloud-setup.md](https://github.com/xop1tt/CLIENTS/blob/main/docs/cloud-setup.md).

**Иконка:** значок один и тёмный. Исходник `Resources/AppIcon.svg`, растр `AppIcon-1024.png` строит `scripts/make-icon.py` (Pillow), при сборке из него получается `AppIcon.icns`. Светлого варианта и подмены значка в Dock нет: при выходе Dock показывает значок из пакета, и подменённый слетал на светлый. Центр буквы и отступы проверяют `tests/test_icon.py` и `IconTests`.

### Задел под сервер

Поиск вынесен в отдельный модуль `LeadSearch`, который не зависит от интерфейса:

- `SearchEngine` получает настройки, транспорт (`HTTPTransport`) и хранилище (`SearchRepository`);
- настройки источников (`SearchSettings`) хранятся как JSON — тот же формат сможет читать сервер;
- локальный вход идёт через протокол `AuthService` (реализация `LocalAuthService`), облачный — через модуль `LeadCloud`.

Чтобы перенести поиск на сервер и не держать Mac включённым, достаточно запустить тот же `SearchEngine` на сервере со
своим хранилищем. Это следующий этап.

### Тесты и проверки как эталон

Каждый модуль и каждая функция проверяются на эталонном уровне: основной сценарий, граничные случаи, ошибки и безопасность (секреты, права, защита от подмены данных). Карта покрытия по модулям: [Тестирование](Тестирование).

Правила после того, как тесты доведены до эталона:

- Тесты не меняются, чтобы «позеленить» сборку. Красный тест означает ошибку в коде, и правится код.
- Тест меняется, только если это необходимо для подключения новой функции и проверка старого поведения от этого не слабеет: старые случаи остаются, добавляются новые.
- Новая функция приходит со своими тестами по тому же эталону: в новых файлах или новых тестовых классах.
- Ослаблять и отключать проверки, пропускать тесты и менять пороги нельзя. Исключение только по прямому решению владельца проекта.

## CI

| Workflow | Когда | Что делает |
|---|---|---|
| **Tests** (`tests.yml`) | push в main, каждый PR | тесты Python-версии с проверкой покрытия строк (не ниже 90%); обязательная проверка для слияния |
| **macOS app** (`macos-app.yml`) | изменения в `macos/` | в каждом PR: `swift test` (ядро, поиск, облако, интерфейс) и сводка покрытия по модулям. После слияния в main дополнительно: универсальная сборка, смоук-тест запуска, dmg в Artifacts |
| **Cloud** (`cloud.yml`) | изменения облака | локальный стенд Supabase и тесты входа, лимитов, RLS, синхронизации; сборка ядра на Linux |
| **CodeQL (Swift)** (`codeql-swift.yml`) | только main и раз в неделю | анализ Swift с полной сборкой (около 15 минут) |
| **Release** (`release.yml`) | тег `v*` или вручную | один релиз для обеих систем: тесты и сборка dmg (macOS) и установщика (Windows) параллельно, затем один GitHub Release с заметками, обоими файлами и SHA-256; при падении любой сборки релиз не создаётся |
| **Lead search** / **Diagnose** | вручную | [поиск в GitHub Actions](Поиск-в-GitHub-Actions) |
| **Wiki** (`wiki.yml`) | изменения в `wiki/` в main | публикует страницы из папки `wiki/` в Wiki репозитория |
| Dependency review, Dependabot auto-merge | PR | проверка зависимостей |

**Правило по времени.** В PR идут все тесты, кроме полной сборки приложения, и каждая проверка в PR ограничена 10 минутами. Всё, что может идти дольше 10 минут (полная сборка, анализ Swift, релиз), запускается только при слиянии в main. Новую долгую проверку добавляйте в workflow с условием `if: github.event_name != 'pull_request'`.

Устаревшие запуски одной ветки отменяются автоматически (`concurrency`), поэтому серые «cancelled» — это не ошибка.

## Подпись релизов

Платного Apple Developer ID нет. Без настроек релиз подписывается ad-hoc: подпись у каждой сборки своя, и после
каждого обновления Связка ключей снова спрашивает пароль. Чтобы подпись была одинаковой у всех версий, один раз
создайте собственный сертификат на своём Mac:

```bash
brew install gh && gh auth login   # если gh ещё нет
./macos/scripts/make-signing-certificate.sh
```

Скрипт создаёт самоподписанный сертификат подписи кода на 20 лет и кладёт его в секреты репозитория
`MACOS_SIGN_P12` и `MACOS_SIGN_PASSWORD`. `release.yml` импортирует его во временную связку ключей и подписывает
им приложение; если секретов нет или подпись не удалась, используется ad-hoc. Сертификат не создавайте заново:
новый снова сменит подпись. На Gatekeeper это не влияет: при первом запуске скачанного dmg всё так же нужно
«Открыть».

## Выпуск релиза

1. Добавьте заметки в `.github/release-notes/vX.Y.Z.md` (что нового, исправлено, установка) и слейте PR в `main`.
2. **Actions → Release → Run workflow**, ветка `main`, в поле `tag` — например `v1.0.6`.
3. Workflow поставит тег на выбранный коммит, соберёт приложение и прикрепит `Customers-vX.Y.Z-macOS.dmg` к релизу.

Приложения с версии 1.0.5 увидят новый релиз в течение суток (см. [Обновления](Обновления-и-отчёты-о-сбоях)).

## Как добавить источник или адаптер (Python-версия)

**Ещё одна RSS-лента** — кода не нужно, см. [Поиск в GitHub Actions](Поиск-в-GitHub-Actions#6-настроить-источники).

**Новый тип источника:**

1. Создайте класс в `src/leadgen/sources/`, унаследуйте его от `Source` и реализуйте `fetch(since, cursor) -> FetchResult`.
2. Зарегистрируйте класс в `sources/registry.py`.
3. Добавьте блок в конфиг.
4. Напишите тест на фикстуре.

Новый адаптер подключается так же: класс от `Adapter` с методом `process(lead)`, регистрация в `integrations/registry.py`.

Правило проекта для любых новых источников и сервисов: только бесплатно навсегда (без пробных периодов и платных API)
и только в рамках условий площадки.

## Как править эту Wiki

Страницы лежат в папке [`wiki/`](https://github.com/xop1tt/CLIENTS/tree/main/wiki) репозитория и правятся через PR, как код.
После слияния в `main` workflow **Wiki** публикует их сам. Правки прямо в веб-интерфейсе Wiki будут перезаписаны.
Ссылки между страницами — по имени файла без `.md`, например `[Установка](Установка)`.

## Как предложить изменение

1. Сделайте ветку или форк и откройте Pull Request в `main`.
2. Дождитесь зелёной проверки **Tests** (и **macOS app**, если меняли приложение).
3. Владелец репозитория проверяет все изменения (`CODEOWNERS`).
