## Сборка приложения

Нужны Node.js 22+ и Rust (stable). На macOS ещё Xcode Command Line Tools (`xcode-select --install`), на Linux (только для
разработки и тестов) пакеты `libwebkit2gtk-4.1-dev libsoup-3.0-dev libayatana-appindicator3-dev librsvg2-dev`.

```bash
cd desktop
npm ci
npm run dev                                       # интерфейс в браузере с демо-данными
npm run dev:beta                                  # настоящее приложение (канал Beta: свои данные, Stable не трогает)
npm run typecheck && npm test                     # типы и тесты интерфейса (Vitest)
cargo test --manifest-path src-tauri/Cargo.toml   # тесты ядра
npx tauri build --bundles app --target universal-apple-darwin   # macOS: Customers.app (Apple Silicon + Intel)
./scripts/make-dmg.sh out/Customers.dmg src-tauri/target/universal-apple-darwin/release/bundle/macos/Customers.app
```

Облако включается в сборке переменными окружения `SUPABASE_URL` и `SUPABASE_ANON_KEY` (только публичный ключ), см.
[docs/cloud-setup.md](https://github.com/xop1tt/CLIENTS/blob/main/docs/cloud-setup.md). Ключи OAuth для дисков:
`GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, `DROPBOX_APP_KEY`, `MICROSOFT_CLIENT_ID`.

**Иконка:** значок один и тёмный. Исходник `desktop/src-tauri/icons/AppIcon.svg`, растр `source.png` строит `scripts/make-icon.py`
(Pillow), остальные размеры, `icon.icns` и `icon.ico` делает `npx tauri icon src-tauri/icons/source.png`. Светлого варианта и
подмены значка в Dock нет. Центр буквы и отступы проверяет `tests/test_icon.py`.

## Сборка приложения для Windows

Нужны Windows 10/11 x64, Node.js 22+, Rust (stable, MSVC) и для установщика бесплатный Inno Setup 6. Visual Studio для запуска не нужна
(для сборки Rust нужны «Build Tools для Visual Studio» с компонентом C++).

```powershell
cd desktop
npm ci
npx tauri build --no-bundle                       # src-tauri\target\release\customers.exe
New-Item -ItemType Directory dist-installer -Force
Copy-Item src-tauri\target\release\customers.exe dist-installer\Customers.exe
iscc /DAppVersion=1.2.3 /DSourceDir="$PWD\dist-installer" /DOutputDir="$PWD\artifacts" installer\Customers.iss
./installer/check.ps1 -Artifacts artifacts        # установка, поверх, удаление
```

Приложению нужна среда WebView2: она есть в Windows 11 и в обновлённой Windows 10; если её нет, установщик об этом сообщит.

### Тесты и проверки как эталон

Каждый модуль и каждая функция проверяются на эталонном уровне: основной сценарий, граничные случаи, ошибки и безопасность (секреты, права, защита от подмены данных). Карта покрытия по модулям: [Тестирование](Тестирование).

Правила после того, как тесты доведены до эталона:

- Тесты не меняются, чтобы «позеленить» сборку. Красный тест означает ошибку в коде, и правится код.
- Тест меняется, только если это необходимо для подключения новой функции и проверка старого поведения от этого не слабеет: старые случаи остаются, добавляются новые.
- Новая функция приходит со своими тестами по тому же эталону: в новых файлах или новых тестовых классах.
- Ослаблять и отключать проверки, пропускать тесты и менять пороги нельзя. Исключение только по прямому решению владельца проекта.

## CI

| Workflow | Когда | Что делает |
|---|---|---|
| **Tests** (`tests.yml`) | push в main, каждый PR | тесты Python-версии с проверкой покрытия строк (не ниже 90%); обязательная проверка для слияния |
| **Desktop** (`desktop.yml`) | изменения в `desktop/` | `frontend`: типы, тесты интерфейса, сборка; `rust`: тесты ядра на Linux, macOS и Windows; `build`: сборка приложения под macOS (универсальное, с проверкой архитектур) и Windows |
| **Cloud** (`cloud.yml`) | изменения облака | локальный стенд Supabase и тесты входа, лимитов, RLS, синхронизации; сквозные тесты Rust-ядра на Linux |
| **CodeQL** (`codeql.yml`) | каждый PR, main и раз в неделю | анализ Rust, TypeScript, Python и Actions |
| **Release** (`release.yml`) | тег `v*` или вручную | один релиз для обеих систем: тесты и сборка dmg (macOS) и установщика (Windows) параллельно, затем один GitHub Release с заметками, обоими файлами и SHA-256; при падении любой сборки релиз не создаётся |
| **Lead search** / **Diagnose** | вручную | [поиск в GitHub Actions](Поиск-в-GitHub-Actions) |
| **Wiki** (`wiki.yml`) | изменения в `wiki/` в main | публикует страницы из папки `wiki/` в Wiki репозитория |
| Dependency review, Dependabot auto-merge | PR | проверка зависимостей |

**Правило по времени.** В PR идут все тесты, и каждая проверка в PR ограничена 10 минутами. Всё, что может идти дольше (подписанная сборка, релиз), запускается только при слиянии в main или по тегу. Новую долгую проверку добавляйте в workflow с условием `if: github.event_name != 'pull_request'`.

Устаревшие запуски одной ветки отменяются автоматически (`concurrency`), поэтому серые «cancelled» — это не ошибка.

## Подпись релизов

Установщик Windows не подписывается (сертификата Microsoft нет). Для macOS платного Apple Developer ID нет. Без настроек релиз подписывается ad-hoc: подпись у каждой сборки своя, и после
каждого обновления Связка ключей снова спрашивает пароль. Чтобы подпись была одинаковой у всех версий, один раз
создайте собственный сертификат на своём Mac:

```bash
brew install gh && gh auth login   # если gh ещё нет
./scripts/make-macos-signing-certificate.sh
```

Скрипт создаёт самоподписанный сертификат подписи кода на 20 лет и кладёт его в секреты репозитория
`MACOS_SIGN_P12` и `MACOS_SIGN_PASSWORD`. `release.yml` импортирует его во временную связку ключей и подписывает
им приложение; если секретов нет или подпись не удалась, используется ad-hoc. Сертификат не создавайте заново:
новый снова сменит подпись. На Gatekeeper это не влияет: при первом запуске скачанного dmg всё так же нужно
«Открыть».

## Выпуск релиза

1. Добавьте заметки в `.github/release-notes/vX.Y.Z.md` (что нового, исправлено, установка) и слейте PR в `main`. Без файла заметок релиз получит автоматические.
2. **Actions → Release → Run workflow**, ветка `main`, в поле `tag` — например `v1.1.2` (допустимы `vX.Y.Z` и `vX.Y.Z.W`). Релиз запускается и пушем тега `v*`.
3. Задачи `macos` и `windows` собираются параллельно без прав на запись; `publish` (единственная с `contents: write`) ждёт обе, ставит тег на выбранный коммит и создаёт один релиз: `Customers-vX.Y.Z-macOS.dmg`, `Customers-vX.Y.Z-Windows-x64-Setup.exe` и `.sha256` для каждого. Если любая сборка упала, релиз не создаётся. Версия берётся из тега для обеих систем.

Первый релиз единым workflow: v1.1.1 (запуск 7 ноября 2026, успешно, четыре файла).

Приложения с версии 1.0.5 увидят новый релиз в течение суток (см. [Обновления](Обновления-и-отчёты-о-сбоях)).

## Как добавить источник или адаптер (Python-версия)

**Ещё одна RSS-лента** — кода не нужно, см. [Поиск в GitHub Actions](Поиск-в-GitHub-Actions#6-настроить-источники).

**Новый тип источника:**

1. Создайте класс в `src/leadgen/sources/`, унаследуйте его от `Source` и реализуйте `fetch(since, cursor) -> FetchResult`.
2. Зарегистрируйте класс в `sources/registry.py`.
3. Добавьте блок в конфиг.
4. Напишите тест на фикстуре.

Новый адаптер подключается так же: класс от `Adapter` с методом `process(lead)`, регистрация в `integrations/registry.py`.

Правило проекта для любых новых источников и сервисов: только бесплатно навсегда (без пробных периодов и платных API)
и только в рамках условий площадки.

## Как править эту Wiki

Страницы лежат в папке [`wiki/`](https://github.com/xop1tt/CLIENTS/tree/main/wiki) репозитория и правятся через PR, как код.
После слияния в `main` workflow **Wiki** публикует их сам. Правки прямо в веб-интерфейсе Wiki будут перезаписаны.
Ссылки между страницами — по имени файла без `.md`, например `[Установка](Установка)`.

## Как предложить изменение

1. Сделайте ветку или форк и откройте Pull Request в `main`.
2. Дождитесь зелёной проверки **Tests** (и **Desktop**, если меняли приложение).
3. Владелец репозитория проверяет все изменения (`CODEOWNERS`).

## Каналы Stable и Beta

Отладочная сборка всегда работает как **Customers Beta** — отдельное приложение со своими папками данных,
секретами, ссылками и облаком. `npx tauri dev` без beta-конфигурации остановится с объяснением, чтобы не открыть
данные установленной Stable-версии. Подробности и команды — `docs/DEBUG_BUILD.md`, `docs/DEVELOPMENT_WORKFLOW.md`.
